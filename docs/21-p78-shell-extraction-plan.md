# План облегчения p78: HTML-оболочка и внешние части

## 1. Исходное состояние

`prototype/p78-living-ring-interface.html` одновременно содержит:

- HTML-разметку интерфейса;
- около 35 КБ встроенного CSS;
- около 130 КБ встроенного browser runtime;
- порядок загрузки независимых семантических модулей.

На момент замера файл занимает 183 561 байт и 2 150 строк. Основная проблема не в сетевом весе как таковом, а в смешении ответственности: любое изменение затрагивает один большой документ, тесты ищут код внутри HTML, а параллельная работа создаёт конфликты.

## 2. Целевая структура первого этапа

```text
prototype/
  p78-living-ring-interface.html       # только документ, элементы и порядок зависимостей
  p78-living-ring-interface.css        # все стили страницы
  lib/
    p78-living-ring-runtime.js         # оркестрация canvas и UI без изменения поведения
    semantic-*.js                      # уже существующие предметные контракты
  tests/
    p78-fixture.cjs                    # единый загрузчик shell + runtime для статических тестов
    semantic-p78-shell-regression.cjs  # архитектурные ограничения оболочки
```

Целевой размер HTML после механического выноса: не более 30 КБ. CSS и runtime остаются обычными локальными файлами и кэшируются браузером. Плагин или сборщик для первого этапа не нужен.

## 3. Этап A: механический вынос без смены поведения

1. Перенести содержимое `<style>` в `p78-living-ring-interface.css` без переформатирования.
2. Подключить CSS одним `<link rel="stylesheet">` в `<head>`.
3. Перенести последний встроенный IIFE в `lib/p78-living-ring-runtime.js` без изменения области видимости.
4. Подключить runtime последним классическим `<script src>`, после всех `semantic-*` зависимостей.
5. Не вводить `type="module"` на этом этапе: это изменило бы область видимости и поведение `file://`.
6. Обновить статические тесты: порядок зависимостей проверять по HTML, реализацию функций — по runtime.

Это атомарная миграция: исходный inline-код и внешний файл не должны существовать одновременно.

## 4. Этап B: последовательное дробление runtime

После доказанного равенства поведения внешний runtime можно делить только по устойчивым контрактам:

| Часть | Ответственность | Предлагаемый API |
|---|---|---|
| `p78-runtime-state.js` | единое состояние интерфейса и снимки | `createState`, `snapshot`, `reset` |
| `p78-canvas-renderer.js` | чистая отрисовка кадра | `draw(ctx, snapshot)` |
| `p78-simulation-loop.js` | rAF, такты, бюджет кадра | `start`, `pause`, `measure` |
| `p78-semantic-orchestrator.js` | вызовы semantic-модулей | `recalculate(text, params)` |
| `p78-ui-controller.js` | события элементов и пассивный рендер | `bind`, `render` |

Запрещённый способ дробления: копировать общие изменяемые переменные в несколько файлов. Сначала состояние должно получить явного владельца и снимок, затем потребители принимают снимок как вход.

## 5. Параллельные пакеты работы

Чтобы агенты не меняли один файл одновременно, ответственность разделяется так:

1. **CSS:** создать только `p78-living-ring-interface.css`; HTML не редактировать.
2. **Runtime:** создать только `lib/p78-living-ring-runtime.js`; HTML не редактировать.
3. **Проверка:** создать `tests/p78-fixture.cjs` и `tests/semantic-p78-shell-regression.cjs`; существующие тесты не редактировать.
4. **Сведение:** один владелец изменяет HTML, обновляет старые тесты и версии подключений.

## 6. Приёмочные условия

- HTML не содержит `<style>` и исполняемого inline `<script>`.
- HTML меньше 30 КБ и сохраняет все прежние `id` элементов.
- CSS и runtime существуют как отдельные файлы и не пусты.
- Runtime загружается после всех библиотек, которые он вызывает.
- Внешний runtime синтаксически корректен и содержит ровно один запуск `requestAnimationFrame(frame)`.
- Все существующие семантические регрессии проходят.
- Через `http://localhost/...` загружаются CSS, runtime и три JSON-артефакта без ошибок консоли.
- Ввод, текстовый вывод, `READY/ABSTAIN`, пауза/пуск и движение canvas сохраняют поведение.
- Контрольные скриншоты и метрики кадра подтверждают, что миграция не создала пустой canvas или дублированный цикл.

## 7. Откат

Если внешний runtime не стартует, откатывается только механическое подключение оболочки; предметные `semantic-*` модули не меняются. После успешного этапа A исходный inline-код больше не считается источником истины: источником становится `lib/p78-living-ring-runtime.js`.

## 8. Сведённый агентный план

Три независимых аудита — архитектуры, тестирования и устройства runtime — согласуются в одном принципе: этап A должен быть строго механическим. Изменять формулы, правила семантики, частоту кадров или структуру состояния одновременно с выносом кода запрещено. Любое содержательное изменение выполняется отдельным этапом после доказанного равенства поведения.

### 8.1. Граф загрузки и точка запуска

1. HTML создаёт DOM и сохраняет все текущие `id`.
2. В `<head>` загружается `p78-living-ring-interface.css`.
3. Внизу документа в прежнем порядке загружаются все `semantic-*` зависимости.
4. `semantic-language.js` загружается до модулей, которые обращаются к `window.MRDSemanticLanguage`.
5. `lib/p78-living-ring-runtime.js` загружается последним и только один раз.
6. Внешний runtime выполняет прежнюю последовательность старта: подготовка данных, первичный расчёт условия и единственный запуск `requestAnimationFrame(frame)`.

На этапе A используются обычные `<script src>`, без `type="module"`, `async` и `defer`. Это сохраняет синхронный порядок, глобальные контракты `window.MRDSemantic*` и совместимость с локальным открытием.

### 8.2. Стоп-условия этапа A

Работа немедленно останавливается и возвращается к последнему зелёному состоянию, если обнаружено хотя бы одно из условий:

- отсутствует ожидаемый DOM-элемент или изменился его `id`;
- runtime стартует раньше зависимости либо объект `MRDSemantic*` отсутствует;
- `initializeSemanticDataEvidence`, первичный расчёт или цикл кадров не запускаются;
- цикл кадров, обработчик события или вывод регистрируется дважды;
- какой-либо тест начинает требовать содержательного изменения формулы ради прохождения миграции;
- в браузере появляется ошибка загрузки, пустой canvas или прекращается обновление состояния.

При таком сбое откатывается только подключение оболочки. Вынесенные файлы сохраняются для диагностики, а семантические модули не переписываются под ошибочную оболочку.

## 10. Контракт общей тестовой фикстуры

`prototype/tests/p78-fixture.cjs` должен экспортировать как минимум:

- абсолютные пути `htmlPath`, `cssPath`, `runtimePath`;
- строки `html`, `css`, `runtime`;
- `combinedSource` для переходных статических проверок;
- `scriptSources` в фактическом порядке HTML;
- `styleSources`;
- `domIds` и список дубликатов;
- функцию проверки относительного порядка двух подключений.

Фикстура не исполняет браузерный runtime и не имитирует DOM. Её задача — дать статическим регрессиям единый источник после физического разделения файлов.

Архитектурная проверка оболочки фиксирует следующие инварианты:

- ровно один внешний CSS страницы;
- ровно один внешний runtime страницы;
- локальные CSS/JS подключены с параметром версии;
- runtime расположен после всех вызываемых зависимостей;
- отсутствуют `<style>`, обработчики вида `onclick=` и исполняемые inline-скрипты;
- нет повторяющихся `id`;
- runtime не содержит `eval`, `new Function` и внешних сетевых адресов;
- присутствует один старт цикла кадров.

## 11. Этап B: детальная декомпозиция runtime

Этап B выполняется отдельными небольшими изменениями. Перед переносом функций вводится один явный владелец состояния с четырьмя разделами:

| Раздел | Содержимое | Кто может изменять |
|---|---|---|
| `worldState` | частицы, кольца, острова, связи, следы, осколки, счётчик тактов | только симуляция |
| `reactionState` | поле реакции, очередь пересчёта, ревизии, расписание обновлений | только ядро реакции |
| `semanticState` | анализ текста, решение, доказательства, журнал, продолжение | семантическая транзакция |
| `uiState` | активная панель, история маршрута, пауза, ссылки DOM | контроллер интерфейса |

Потребители получают неизменяемый снимок, а не общие изменяемые переменные.

### B1. Владелец состояния

- ввести `createState`, `snapshot`, `reset`;
- не менять формулы и начальные значения;
- зафиксировать тестами создание и снимок состояния.

### B2. Ядро реакции

Вместе переносятся состояние реакции и функции инициализации, продвижения, планирования, сброса очереди и формирования снимка. Их нельзя распределять между агентами, потому что они разделяют ревизии и флаги расписания.

### B3. Чистые упаковщики данных

Независимо можно переносить функции, которые строят объекты для отображения: пакеты анализа, решения, трассы, доказательств и параметров. После них отдельно переносятся DOM-рендереры, принимающие готовый пакет.

### B4. Семантическая транзакция

Вместе остаются `commitSemanticAction`, текстовое продолжение, завершение действия, квитанция, запись журнала, undo/replay и обновление ledger. Это одна атомарная операция и один владелец записи.

### B5. Цикл симуляции и canvas

`frame`, `step`, `draw`, обновление панели и метрики кадра переносятся последними. Цикл потребляет снимки и не запускает тяжёлый семантический анализ внутри каждого кадра.

### B6. События интерфейса

После стабилизации API контроллер связывает DOM-события с командами состояния. Обработчики не изменяют внутренние структуры напрямую.

## 12. Производительность и проверка этапа B

До и после каждого шага сохраняются ограничения:

- `SIMULATION_SUBSTEP_CAP = 2`;
- `VISUAL_PARTICLE_COUNT <= 180`;
- `REACTION_RUNTIME_PARTICLE_LIMIT <= 96`;
- `TRACE_LIMIT <= 120`;
- `FRAME_HEALTH_WINDOW = 180`;
- тяжёлые семантические пакеты рассчитываются вне кадрового цикла и применяются одним снимком.

Целевой рабочий кадр занимает до 16 мс. Для текущего встроенного браузера приёмочное наблюдение — устойчивый `p95 <= 40 мс` без периодического длительного зависания. Производительность проверяется в браузере, но не превращается в нестабильный CI-тест Node.

Для каждого выделенного модуля требуются узкие проверки:

- утилиты и анализ — детерминированность на фиксированном вводе;
- ядро реакции — ревизии, расписание и сброс очереди на поддельном времени;
- упаковщики и рендереры — таблица входов/выходов и отсутствие записи в состояние;
- транзакция — commit, undo и replay;
- цикл кадров — поддельные таймеры, единственный rAF и корректные метрики;
- итог — браузерная проверка известной и неизвестной фразы через `localhost`.

## 13. Распределение исполнения между агентами

| Пакет | Владелец | Зависимость | Разрешённые файлы |
|---|---|---|---|
| A1 | агент фикстуры | A0 | `tests/p78-fixture.cjs`, `tests/semantic-p78-shell-regression.cjs` |
| A2.1 | агент тестов 1 | A1 | только пять тестов группы 1 |
| A2.2 | агент тестов 2 | A1 | только шесть тестов группы 2 |
| A3 | основной агент | A0, параллельно A2 | HTML и версии подключений |
| A4 | основной агент | A2, A3 | запуск проверок и браузер, без функциональных нововведений |
| B1-B2 | один агент состояния | успешный A4 | новые файлы состояния и реакции |
| B3 | несколько агентов | B1 | непересекающиеся чистые упаковщики |
| B4 | один агент транзакции | B1 | транзакционный модуль и его тесты |
| B5-B6 | основной агент | B2-B4 | цикл кадров, canvas и привязка DOM |

Агенты B3 могут работать параллельно. Общие мутации мира, семантическая транзакция, планировщик реакции и цикл кадров всегда имеют по одному владельцу.
## 14. Фактический результат этапа A

Этап A выполнен 19 июля 2026 года после фиксации плана и разделения областей записи.

- HTML уменьшен с 183 561 до 11 781 байта; встроенных <style> и исполняемых inline-скриптов нет.
- CSS вынесен в prototype/p78-living-ring-interface.css, runtime — в prototype/lib/p78-living-ring-runtime.js.
- Созданы общая фикстура и архитектурная регрессия оболочки; 11 старых тестов переведены на раздельное чтение HTML и runtime.
- Языковой контракт подключён до потребителей; проверены омонимия, согласование, валентность и честная обработка неизвестных слов.
- Для нулевого языкового покрытия текстовый результат теперь возвращает abstain / LANGUAGE_COVERAGE, не создаёт вставляемую строку и отключает кнопку вставки.
- Полный итог: 17/17 suites, 190/190 checks.
- Через XAMPP подтверждены загрузка страницы и локальных данных, dataStatus=READY, отсутствие ошибок консоли, распознавание key.object, грамматика PASS, безопасное УТОЧНИТЬ для OOV, а также остановка и возобновление тактов.
- В устойчивом браузерном замере frameP95 составил около 34 мс, собственная работа кадра — 4–7 мс. Редкие длинные интервалы совпадали с удалёнными операциями контроля вкладки; поэтому они зафиксированы как отдельный предмет этапа B, а не как причина менять формулы этапа A.

Этап B не начинался. Его первый допустимый шаг — явный владелец состояния B1; прямое параллельное дробление текущих общих мутаций по-прежнему запрещено.
