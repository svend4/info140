## Характеристики частиц: однотипные или разнотипные?

### 1. Где мы сейчас и почему этого мало

Сегодня инфон описывается фактически тремя числами:

| Что есть сейчас | Символ | Диапазон | Роль |
|---|---|---|---|
| Класс / уровень обобщённости | `lv` | C0..C5 (0..5) | определяет «крупность» смысла |
| Масса | `m` | >0 | сохраняемая величина при split/merge |
| Заряд (в части прототипов) | `q` | ±1 | грубое притяжение/отталкивание |

Реакции включаются **глобальным** рычагом λ, а исход встречи (06.7) считается по «заряд + близость классов». Это означает, что **поведение частицы почти полностью определяется снаружи** (значением λ), а не её собственным внутренним состоянием. Частицы взаимозаменяемы: два инфона одного класса и массы ведут себя идентично в любой ситуации.

**Ограничения однородности именно для цепных реакций:**

- **Нет «химии».** Цепная реакция требует, чтобы продукт одной встречи менял условия следующей. Если у частицы нет атрибутов, которые встреча *изменяет* (кроме массы/класса), то каскад вырождается в простую серию split/merge — он затухает или взрывается монотонно, без структуры.
- **Нет избирательности.** «А реагирует с B, но не с C» невозможно выразить: все пары одного класса эквивалентны. Значит нельзя получить специфические пути реакций — основу любого семантического конвейера.
- **Нет катализа и ингибирования.** Чтобы одна частица *влияла* на реакцию других, не расходуясь, нужен атрибут-катализатор. В текущей модели влиять можно только массой.
- **Нет направленности и насыщения.** Без «сколько связей осталось» (валентность) частица либо инертна, либо сливается со всем подряд — нет промежуточных структур (молекул, цепочек).
- **Смысл не виден.** `lv+m` говорят о размере, но не о *теме*. Две буквы C0 «к» и «z» неотличимы — значит нельзя собрать осмысленное слово против бессмысленного набора.

Вывод: однотипность хороша для демонстрации самого рычага λ, но потолок выразительности достигается мгновенно — каскад не может стать *семантическим*, только количественным.

### 2. Предлагаемый расширенный набор атрибутов

Идея: разделить атрибуты на три слоя — **скалярные** (число, дёшево считать), **векторные** (тема/аффинность, дают избирательность) и **структурные** (связи, payload). Конвейер строится постепенным включением слоёв.

| Имя | Символ | Тип / диапазон | Смысл | На что влияет |
|---|---|---|---|---|
| Класс / уровень обобщённости | `lv` | enum C0..C5 | крупность смысла (буква → ядро) | пороги split/merge, визуальный слой геометрии |
| Масса | `m` | float > 0 | сохраняемое «вещество» смысла | продукты реакции (делится/суммируется) |
| Полярность / заряд | `q` | float ∈ [−1, +1] | семантический знак (тезис/антитезис, +/−) | притяжение/отталкивание; знак вклада в реакцию |
| Валентность | `v` | int 0..6 | сколько связей частица может держать | насыщение, образование «молекул»-структур |
| Аффинность (домены) | `a⃗` | вектор тегов, напр. 8 осей ∈ [0,1] | к каким темам тяготеет (право/эмоция/число…) | избирательность: с кем вообще реагирует |
| Спин / контекст | `s` | enum {↑,↓} или угол [0,2π) | «ракурс» смысла, в каком контексте активен | разрешение/запрет реакции по совпадению контекста |
| Энергия / температура | `E` | float ≥ 0 | подвижность, готовность реагировать | скорость, порог инициации каскада, остывание |
| Когерентность | `κ` | float ∈ [0,1] | качество/чистота смысла (1=ядро, 0=шум) | вероятность удачного синтеза vs распада |
| Энтропия | `S` | float ∈ [0,1] | беспорядок, κ ≈ 1−S | дрейф к λ→0, спонтанный распад |
| Возраст / полупериод | `τ` | float (тики); `t½` | старение, время полураспада | спонтанный split, «забывание» |
| Семантическая нагрузка | `payload` | строка/набор токенов + тема | собственно носимый смысл («к», «дом», тема) | конкатенация при merge, проверка осмысленности |

**Обоснование ключевых (почему именно эти):**

- **Полярность `q` как float, а не ±1.** Непрерывный знак позволяет частичную нейтрализацию (`q₁+q₂≈0` → стабильная пара) и градации «силы тезиса». Это уже даёт нелинейный исход встречи вместо бинарного.
- **Валентность `v`** — единственный атрибут, дающий *структуру* (молекулы, цепочки). Без неё каскад — это поток, а не сборка. `v` убывает с каждой связью → естественное насыщение, каскад сам себя ограничивает.
- **Аффинность `a⃗`** — сердце избирательности. Реакция возможна, если `a⃗₁·a⃗₂` (косинусная близость) выше порога. Именно вектор (а не один тег) даёт «частично совпадающие темы» → богатые, но не хаотичные пути.
- **Энергия `E`** — топливо каскада. Экзотермический merge поднимает `E` соседей выше порога → они тоже реагируют → **самоподдерживающаяся цепная реакция** (как в горении). Это прямой ответ на запрос заказчика.
- **Когерентность/энтропия `κ`/`S`** — переводят λ из глобального параметра в *локальное* свойство частицы: κ→1 это локальное обобщение, S→1 локальное дробление. Появляется внутренняя «погода» смысла.
- **`payload`** — то, что делает реакцию *семантической*, а не просто числовой: при merge токены конкатенируются («к»+«о»+«т»→«кот»), осмысленность проверяется словарём/эвристикой и влияет на κ продукта.

**Производные величины (не хранить, а вычислять):**

- Совместимость пары: `compat = cos(a⃗₁,a⃗₂) · spin_match(s₁,s₂) · class_proximity(lv₁,lv₂)`
- Знак исхода: `q₁·q₂ < 0` → тяга к слиянию; `> 0` → отталкивание/обмен.
- Порог реакции: реакция идёт, если `E₁+E₂ ≥ E_threshold(lv)` и `compat ≥ θ`.

### 3. Однородность vs разнотипность — разбор

**Подход A. Однородные частицы (текущий: lv, m, ±q)**

Плюсы:
- Простота модели и кода; легко объяснить игроку и отладить.
- Высокая производительность: тысячи частиц, дешёвые проверки.
- Предсказуемый баланс: мало степеней свободы → легко не «сломать» систему.
- Чистая демонстрация самого рычага λ без посторонних эффектов.

Минусы:
- Потолок выразительности: каскады только количественные (больше/меньше массы).
- Нет избирательности, катализа, структур → нет настоящей «химии смысла».
- Нет места для редактора правил: нечего настраивать, кроме порогов.
- Смысл не репрезентирован — игра *про смысл*, но частицы его не несут.

**Подход B. Разнотипные частицы (атрибуты + формулы)**

Плюсы:
- Выразительность: «А реагирует с B, не с C», катализ, ингибирование, цепочки.
- Эмерджентность: из простых правил рождаются неожиданные устойчивые структуры (молекулы, автокаталитические циклы).
- Естественная база для редактора правил (атрибуты = переменные формул).
- Смысл становится наблюдаемым: payload, аффинность, когерентность видны игроку.

Минусы:
- Сложность баланса: больше степеней свободы → легко получить «всё взрывается / всё затухает».
- Производительность: векторные аффинности и проверки пар дороже (нужен пространственный хэш/соседство).
- Кривая обучения игрока круче; нужна прогрессивная подача атрибутов.
- Риск over-engineering: часть атрибутов может не «зазвучать» в геймплее.

**Рекомендация:** не выбирать крайность, а двигаться по слоям — начать с минимального расширения (ближе к A), включать атрибуты по одному, проверяя, что каждый *виден* в поведении. Разнотипность вводится дозированно.

### 4. Поэтапное внедрение

**Этап 0 — Примитив (минимальное расширение, +2 атрибута).**
К текущим `lv, m` добавить только:
- `q` ∈ [−1,+1] (непрерывный) — уже даёт нейтрализацию и нелинейный исход;
- `a` — **один** доменный тег (enum из ~4–6 тем) вместо вектора.

Правило встречи: реакция, если теги совпадают (`a₁=a₂`) и `q₁·q₂<0`. Этого достаточно, чтобы появилась **избирательность** и первые осмысленные пары — без векторной математики. Дёшево, наглядно, легко балансировать.

**Этап 1 — Средний уровень (+ энергия, валентность, аффинность-вектор).**
- `E` (энергия/температура) + порог реакции → **самоподдерживающийся каскад** (экзотермический merge греет соседей).
- `v` (валентность) → структуры/молекулы и естественное насыщение каскада.
- `a` превращается в вектор `a⃗` (4–8 осей) → частичная совместимость через косинус, богатые пути реакций.
- Вводится `payload` (токены) → merge конкатенирует смысл, словарь проверяет осмысленность.

На этом уровне уже работает **семантический конвейер**: примитивы C0 с тегами → по совместимости и энергии собираются в C1..C2 со связной темой и payload.

**Этап 2 — Полный набор + редактор.**
- Добавить `κ/S` (локальная λ), `s` (спин/контекст), `τ/t½` (старение, полураспад) — тонкая «химия» и динамика во времени.
- Все атрибуты становятся **переменными формул** в редакторе правил: условие (`cos(a⃗)>θ ∧ q₁q₂<0 ∧ E>E_th`) → действие (merge/split/обмен/катализ) → модификаторы продукта (`κ`, `payload`, `q`).
- Игрок проектирует собственные реакции — это и есть переход от заданной химии к **конструируемой**.

**Принцип всего пути:** один новый атрибут за итерацию, и каждый обязан давать *наблюдаемое* изменение поведения; если не даёт — откатываем. Так разнотипность наращивается без потери управляемости и баланса.

## Полярность, условия, формулы: как одна частица влияет на другие и возникает цепная реакция

Сейчас инфон в прототипе — это, по сути, пара чисел `(lv, m)` плюс иногда `q`, а «реакция» — глобальный переключатель `split/merge` по λ. Частицы реагируют на λ, но **не друг на друга**: нет акта, где одна частица читает атрибуты другой и меняет их. Этот раздел вводит недостающий слой — **формальное правило взаимодействия** — и показывает, как из него вырастает семантическая цепная реакция, оставаясь под контролем рычага λ.

### Шаг 0. Что добавить в атрибут-вектор инфона

Чтобы частицы стали разнотипными, расширяем состояние от `(lv, m)` до вектора. Это фундамент для всех правил ниже.

| Атрибут | Тип | Диапазон | Смысл / роль во взаимодействии |
|---|---|---|---|
| `lv` | int | C0..C5 | класс (есть сейчас) |
| `m` | float | >0 | масса (есть сейчас) |
| `q` | int | −1,0,+1 | заряд/полярность (частично есть) |
| `tags` | set/bitmask | напр. 16–64 бит | семантические признаки («тема», «домен») — основа сходства |
| `val` | float | [−1,1] | валентность/оценка (заряженность смыслом: «горячая»/«холодная» идея) |
| `act` | float | [0,1] | активация/энергия — расходуется на реакции, регенерирует со временем |
| `thr` | float | [0,1] | личный порог реакции (понижается катализатором) |
| `cd` | int | тики | кулдаун: сколько тиков частица «остывает» после реакции |
| `role` | enum | inert/cat/viral/seed/anti | поведенческая роль (катализатор, вирус, зерно кристаллизации, ингибитор) |
| `bonds` | list | id→вес | связи с другими инфонами (для молекул/кластеров) |

Минимально для старта достаточно `tags`, `q`, `act`, `thr` — остальное вводится поэтапно.

### Шаг 1. Структура правила: УСЛОВИЕ → ЭФФЕКТ

Взаимодействие формализуем как **продукционное правило** (condition–action). Каждое правило — самостоятельный объект, что прямо ведёт к редактору (см. финальный раздел конвейера).

```
Rule {
  id        : string
  arity     : 1 | 2 | N            // на сколько частиц смотрит (соло / пара / окрестность)
  when      : Predicate(a, b, ctx) -> bool   // ctx = {λ, dist, neighbors, tick}
  weight    : Formula -> float     // «сила»/приоритет срабатывания, может зависеть от λ
  prob      : Formula -> [0,1]     // вероятность применения (стохастика)
  effect    : Action(a, b, ctx)    // мутация атрибутов / класса / связей / spawn / kill
  cost      : Formula -> float     // сколько act тратится (тормоз каскада)
  cooldown  : int                  // тики неактивности после срабатывания
  priority  : int                  // разрешение конфликтов
}
```

Ключевой момент: `effect` меняет атрибуты так, что **может выполниться `when` следующего правила** у соседей — это и есть механизм цепи.

### Шаг 2. Библиотека правил (8 конкретных примеров)

Обозначения: `a`, `b` — две частицы; `sim(a,b)` — сходство тегов (см. формулы ниже); `Δq = a.q − b.q`; `dist` — расстояние; λ — глобальный рычаг.

| # | Имя | when (условие) | effect (эффект) | Тип каскада |
|---|---|---|---|---|
| R1 | **Притяжение-слияние** | `Δq ≠ 0 ∧ sim ≥ 0.6 ∧ dist < r` | merge → C(lv+1), `m_new=m_a+m_b`, `tags=tags_a∪tags_b` | кристаллизация |
| R2 | **Отталкивание** | `a.q = b.q ∧ a.q ≠ 0 ∧ dist < r` | импульс расхождения ∝ `1/dist²`; реакции нет | стабилизатор (тормоз) |
| R3 | **Катализатор** | `a.role=cat ∧ contact(a,b)` | `b.thr ← b.thr·(1−κ)` на T тиков (a не тратится) | понижает барьер → разгон |
| R4 | **Вирусное заражение** | `a.role=viral ∧ contact(a,b) ∧ rand<p_inf` | `b.tags ← b.tags ∪ {tag_v}`; `b.role←viral` (с затуханием) | распространение-заражение |
| R5 | **Выравнивание (диффузия)** | `sim ≥ s₀ ∧ dist < r` | `a.val,b.val ← взаимное подтягивание к среднему` (формула ниже) | волна выравнивания |
| R6 | **Лавинное дробление** | `a.act > A_hi ∧ λ < 0.4` | split → 2×C(lv−1), масса делится; осколки получают `act` сверх порога | лавина дробления |
| R7 | **Ингибитор/анти** | `a.role=anti ∧ contact(a,b)` | `b.thr ← b.thr+δ`; `b.act ← b.act·(1−η)` | гаситель каскада |
| R8 | **Зерно кристаллизации** | `a.role=seed ∧ sim ≥ 0.8` | создать `bond(a,b)`; при ≥k связях группа сливается в C(lv+1) | кристаллизация (отложенная) |

Эти восемь покрывают все четыре базовых типа каскада (заражение, лавина, кристаллизация, выравнивание) плюс два тормоза (R2, R7) — необходимый минимум для управляемости.

### Шаг 3. Полярность и формулы влияния

**Сходство тегов** (Жаккар по битовым множествам):
`sim(a,b) = |tags_a ∩ tags_b| / |tags_a ∪ tags_b|`, `sim ∈ [0,1]`.

**Заряд / полярность.** Знак произведения зарядов задаёт притяжение/отталкивание:
`pol(a,b) = −sign(q_a · q_b)` → +1 притяжение (разные знаки), −1 отталкивание (одинаковые), 0 нейтрально.

**Сила влияния** одной частицы на другую (центральная формула):

`F(a→b) = w · sim(a,b) · pol(a,b) · g(λ) / (1 + dist²)`

где `w` — вес правила, `g(λ)` — оконная функция жизни смысла, например `g(λ)=M(λ)=4λ(1−λ)` (влияние максимально в середине рычага, гаснет у полюсов — прямая привязка к ядру концепции).

**Вероятность реакции** (мягкий порог через сигмоиду):

`P_react = σ( β·( F(a→b) − b.thr ) )`, где `σ(x)=1/(1+e^{−x})`, β — «резкость».

Реакция требует энергии: применяется, только если `a.act ≥ cost ∧ b.act ≥ cost`.

**Передача/заражение тега** (R4): `P_inf = p₀ · sim(a,b) · act_a`, затем `tags_b |= tag_v`.

**Выравнивание валентности** (R5, диффузия к среднему с коэффициентом α):
`val_a' = val_a + α·sim·(val_b − val_a)`, `val_b' = val_b + α·sim·(val_a − val_b)`.
При α<0.5 это сжимающее отображение → волна гарантированно затухает (важно для устойчивости).

**Слияние/дробление массы** (инвариант замкнутой системы):
merge: `m' = m_a + m_b` (масса суммируется); split: `m₁+m₂ = m` (делится). Σm по системе сохраняется всегда.

### Шаг 4. Цепная реакция (семантический каскад)

Каскад = последовательность срабатываний, где `effect` одного правила переводит соседей через их `thr`, и у них срабатывает `when`. Четыре канонических типа:

| Тип каскада | Носитель | Что распространяется | Естественный тормоз |
|---|---|---|---|
| Распространение-заражение | R4 (viral) | тег `tag_v` | затухание `act`, ингибитор R7 |
| Лавина дробления | R6 | избыток `act` через осколки | λ↑ (выключает split), расход массы |
| Кристаллизация-слияние | R1/R8 | связи `bond` → укрупнение | исчерпание совместимых соседей, рост `m` (тяжёлые инертны) |
| Волна выравнивания | R5 | сближение `val` | α<0.5 (сжатие), `sim` падает по мере удаления |

**Как λ и тормоза держат каскад между полюсами.** Длина каскада L управляется множителем усиления `γ ≈ ⟨P_react⟩·⟨соседей⟩·(1−затухание)`:
- `γ < 1` → каскад затухает (короткий, безопасный);
- `γ ≈ 1` → «критическое» интересное состояние (длинные, но конечные цепи — целевой режим);
- `γ > 1` → лавина в полюс (всё раздробилось / всё слиплось — смерть смысла).

Рычаг даёт прямой контроль: `g(λ)=4λ(1−λ)` понижает `P_react` у полюсов, поэтому при λ→0 или λ→1 автоматически `γ<1`. Дополнительно: кулдаун `cd` (частица не может срабатывать каждый тик), расход `act` (энергия кончается), ингибиторы R7. Это удерживает систему в «живой» зоне M(λ)≈max.

**Мини-пример (пошагово).** Стартовое поле: один вирусный C1 с `tag=∂` (act=0.9), рядом катализатор `cat`, дальше цепочка совместимых C1.

- **Шаг 1.** R3: катализатор касается соседних C1 → их `thr` падает 0.5→0.35. Барьер снижен.
- **Шаг 2.** R4: вирусный C1 заражает ближайший C1 (`P_inf=p₀·sim·act` высока, т.к. `sim≈0.8`) → сосед получает `tag=∂`, сам становится viral, `act` тратится (0.9→0.6).
- **Шаг 3.** Заражённый сосед (теперь viral, но с меньшим act) заражает следующего; одновременно набралось k носителей `∂` рядом → срабатывает R8/R1: они кристаллизуются в C2 (`m` суммируется, `tags` объединяются).
- **Затухание.** К 4–5 шагу `act` падает ниже `cost`, `cd` блокирует повторы, а укрупнённый C2 тяжёл и инертен → каскад сам гаснет, не дойдя до полюса. Возникла локальная «молекула смысла», а не глобальный коллапс.

### Шаг 5. Псевдокод rule-engine

```python
def tick(particles, rules, λ, ctx):
    fired = []                          # для разрешения конфликтов
    # 1. пространственный индекс: только близкие пары/окрестности
    grid = build_spatial_hash(particles, cell=r_max)

    for a in particles:
        if a.cd > 0:                    # кулдаун — пропуск
            a.cd -= 1
            continue
        neighbors = grid.query(a, r_max)

        # 2. собрать кандидатов-срабатываний
        candidates = []
        for b in neighbors:
            ctx.dist = distance(a, b)
            ctx.λ = λ
            for R in rules:
                if R.arity == 2 and R.when(a, b, ctx):
                    F = R.weight(a, b, ctx)
                    p = R.prob(a, b, ctx)             # = σ(β·(F − b.thr))
                    if a.act >= R.cost and random() < p:
                        candidates.append((R.priority, F, R, a, b))

        # 3. выбрать по приоритету, затем по силе F
        if candidates:
            candidates.sort(key=lambda c: (c[0], c[1]), reverse=True)
            _, _, R, a, b = candidates[0]
            R.effect(a, b, ctx)         # мутация атрибутов / спавн / kill
            a.act -= R.cost; b.act -= R.cost
            a.cd = R.cooldown
            fired.append((R, a, b))

    # 4. отложенные структурные операции (spawn/kill/merge) — батчем
    apply_structural_ops(particles)

    # 5. восстановление и инварианты
    for p in particles:
        p.act = min(1.0, p.act + REGEN)         # регенерация энергии
        p.thr = relax_toward_base(p.thr)        # катализ временный
    assert abs(total_mass(particles) - M0) < eps  # сохранение массы
    return fired
```

Ключевые гарантии движка: (1) **локальность** через spatial hash — O(N·k) вместо O(N²); (2) **детерминизм разрешения конфликтов** — приоритет → сила; (3) **инварианты** — масса проверяется ассертом каждый тик; (4) **тормоза встроены** — кулдаун, расход act, отложенный батч структурных операций (нельзя дважды убить одну частицу за тик).

### Плюсы и минусы формульно-правилового подхода

**Плюсы:**
- **Эмерджентность из малого**: 8 правил + вектор атрибутов дают качественно разное поведение (вирусы, кристаллы, лавины) — богатство без ручного скриптинга каждой ситуации.
- **Прямая привязка к ядру**: λ через `g(λ)=4λ(1−λ)` управляет всеми каскадами разом — рычаг смысла становится буквально регулятором динамики, а не косметикой.
- **Композируемость и редактор**: правило — это объект с полями → естественно выгружается в визуальный редактор «условие→эффект» (мост к конвейеру).
- **Инварианты сохраняются**: масса/замкнутость гарантируются на уровне effect-формул и ассертов.
- **Настраиваемая управляемость**: один множитель γ (через β, cost, cd, α) переводит систему между «скучно затухает» и «интересно живёт».

**Минусы:**
- **Хрупкость баланса**: вблизи γ≈1 система чувствительна к параметрам — легко свалиться в полюс; нужен автотюнинг или «предохранители».
- **Конфликты правил**: при многих правилах растут неоднозначности (что применить первым) — требует дисциплины приоритетов и тестов.
- **Стоимость на масштабе**: окрестностный матчинг и стохастика дороги при больших N; нужен spatial hash и, возможно, бюджет срабатываний на тик.
- **Непрозрачность для игрока**: формульные каскады трудно «прочитать» без визуализации причинности (кто кого заразил/слил) — нужна отладочная подсветка цепей.
- **Тюнинг-ад**: много параметров (`β, κ, α, p₀, cost, cd, thr`) — без пресетов и инструментов калибровки разработка вязнет.

> Вывод для прохода: начать с минимального вектора (`tags, q, act, thr`) и правил R1–R5 на фиксированном λ; убедиться, что `g(λ)` гасит каскады у полюсов; затем добавить роли (R3, R4, R7, R8) и вынести правила в данные — это и есть готовый вход в «семантический конвейер» и редактор правил.

## Семантический конвейер и редактор: от примитивов к среднему уровню и дальше

### 1. Что такое «семантический конвейер»

В текущем прототипе реакции `split`/`merge` включаются **глобально** одним рычагом λ — это «погода для всех». Конвейер переворачивает логику: λ остаётся глобальным климатом, но **локальные узлы-операции** определяют, что именно происходит с потоком инфонов в конкретной точке пространства. Это node-graph в духе Factorio/Houdini/Blueprints, но «трубы» переносят не руду, а **смысл**, и узлы меняют не количество, а **атрибуты / класс / теги** частиц.

Базовая метафора: **инфон течёт по графу и на каждом узле проходит семантическое преобразование**.

| Тип узла | Роль | Что делает с инфоном | Аналог Factorio |
|---|---|---|---|
| **Источник** (`source`) | эмиттер | спавнит инфоны заданного класса/массы/тегов с темпом `rate` | бур/скважина |
| **Преобразователь/Реактор** (`reactor`) | split/merge | применяет правило: делит массу (C↓) или синтезирует (C↑) | плавильня |
| **Фильтр/Условие** (`filter`) | gate | пропускает дальше только если `cond(infon)` истинно | сплиттер с фильтром |
| **Сумматор/Слияние** (`merger`) | агрегатор | копит входы, при наборе массы/числа выдаёт C+1 | сборщик |
| **Разветвитель** (`splitter`) | роутер | направляет инфон по разным портам по условию | сплиттер |
| **Приёмник** (`sink`) | сток/цель | поглощает инфоны, начисляет очки/проверяет цель уровня | хранилище/ракета |

Ключевое отличие от Factorio: **операции семантические**. Реактор не «крафтит предмет X из Y», он трансформирует носитель смысла — понижает/повышает класс, перекрашивает заряд, добавляет тег, домешивает атрибут. Именно на узлах рождается **цепная реакция**: выход одного узла — вход следующего, а условие следующего зависит от того, что сделал предыдущий.

### 2. Лестница сложности

#### Ступень 1 — ПРИМИТИВЫ (атомарные узлы + атомарные правила)

Минимальный кирпич — правило вида **1 условие → 1 эффект**:

```
IF <attr> <op> <value>  THEN  <effect>
```

Примеры атомарных правил:

| Условие | Эффект | Семантика |
|---|---|---|
| `class == C2` | `split → 2×C1` | дробление: «слово → слоги» |
| `q == +` | `route → portA` | сортировка по полярности |
| `m >= 8` | `class += 1` | критическая масса → обобщение |
| `tag has "вода"` | `attr.temp -= 1` | смысловое охлаждение |

Атомарные **узлы** — это `source`, `filter`, `reactor`, `sink` с *одним* правилом. На этой ступени игрок уже строит линейные цепочки: `source → filter → reactor → sink`. Никаких циклов, одно правило на узел.

**Плюсы:** мгновенно понятно, легко балансить, детерминированно.
**Минусы:** выразительность близка к нулю — нет ветвлений, нет «влияния одной частицы на другую».

#### Ступень 2 — СРЕДНИЙ УРОВЕНЬ (рецепты, цепочки, ветвления, обратные связи)

Здесь появляется то, ради чего всё затевается — **семантическая цепная реакция**.

**(а) Рецепты/комбо** — упорядоченный список правил внутри одного узла (первое сработавшее или все по очереди):

```
reactor "Кристаллизатор":
  R1: IF q==+ AND class<=C2  THEN merge_with(nearest q==−)  → class+1
  R2: IF m<2                 THEN destroy (шум рассеялся)
  R3: ELSE                   pass
```

**(б) Влияние частицы на частицу (катализ).** Расширяем модель инфона минимальным набором атрибутов поверх текущих `class/m/q`:

| Атрибут | Тип | Смысл | Пример эффекта |
|---|---|---|---|
| `tags[]` | набор строк | семантические маркеры | «вода»+«огонь» → «пар» |
| `temp` | число | возбуждённость | высокий temp ускоряет реакции рядом |
| `affinity` | вектор | сродство к тегам | определяет, с кем сольётся |
| `charge q` | ± / 0 | полярность (есть) | притяжение/отталкивание |

Тогда правило может **читать соседа и менять его**:

```
IF other.tag has "огонь" AND self.tag has "вода"
THEN self.tag := "пар";  self.temp += 3;  other.consume
```

Это и есть катализ: одна частица **влияет** на другую → у той меняется атрибут → срабатывает её собственное правило → каскад. Длина каскада ограничивается «бюджетом тиков» (анти-зависание).

**(в) Ветвления и обратные связи.** `splitter` по условию шлёт на разные ветви; ветвь может вернуть продукт назад во вход (цикл) — получается автокаталитическая петля (продукт ускоряет собственное производство). Для устойчивости — затухание `temp` со временем и лимит глубины каскада.

Формальная модель срабатывания одного узла за тик:

`out = Σ_i [ rule_i.cond(in, neighbors, λ) ] · rule_i.effect(in)` — первое истинное правило применяется (приоритет сверху вниз), как в CSS/Excel.

**Плюсы:** богатое эмерджентное поведение, настоящие цепные реакции, реиграбельность.
**Минусы:** взрывной рост пространства состояний → нужен предпросмотр и лимиты; баланс становится нетривиальным.

#### Ступень 3 — РЕДАКТОР (визуальный авторинг)

Три парадигмы — рекомендую **гибрид**:

| Парадигма | Сильна в | Слаба в | Кому |
|---|---|---|---|
| **Node-graph** (тянешь узлы/связи) | топология потока, ветвления, петли | мелкая логика внутри узла | визуалам, «фабрика» |
| **Таблица правил** (IF/THEN строки) | плотная логика, много условий | видимость потока | «программистам» |
| **Гибрид** (граф + инспектор-таблица узла) | и то, и другое | сложнее в реализации | **рекомендуется** |

Гибрид: на холсте — **граф узлов и труб**; клик по узлу открывает **инспектор**, где правила узла редактируются как **таблица IF/THEN** + параметры (`rate`, `mass`, пороги). Плюс **библиотека пресетов** (готовые узлы «Дробилка C2», «Сумматор воды»), **предпросмотр** (запуск на тестовом потоке с подсветкой каскада), **сохранение/загрузка** (JSON ↔ localStorage), **шаринг** (экспорт строки/файла).

#### Ступень 4 — ДАЛЕЕ (моды, обучение, генерация)

- **Пользовательские моды**: игрок публикует свой граф+набор правил как «пакет смысла».
- **Обучающие сценарии**: уровень = заданный `source` + целевой `sink` + ограничение на число узлов → «собери конвейер, превращающий C0-буквы в C3-понятие».
- **Генерация уровней**: процедурно задаём цель (какой инфон на выходе) и бюджет, игрок ищет граф; обратная задача — авто-генератор проверяет решаемость симуляцией.

### 3. Модель данных конвейера и редактора

Граф = узлы + порты + связи; узел содержит правила. Всё сериализуемо в JSON.

```js
// Узел
Node = {
  id: "n3",
  type: "reactor",            // source|reactor|filter|merger|splitter|sink
  pos: {x: 320, y: 140},      // для холста + привязка к геометрии (орбита/лепесток)
  params: { rate: 1.0, threshold: 8 },
  ports: {
    in:  [{ id:"in0" }],
    out: [{ id:"out0" }, { id:"out1" }]   // splitter → 2 выхода
  },
  rules: [ /* Rule[] — приоритет по порядку */ ]
}

// Правило (атомарное или комбо-строка)
Rule = {
  id: "r1",
  when: {                              // дерево условий
    all: [ {attr:"class", op:"<=", val:"C2"},
           {attr:"q",     op:"==", val:"+"} ]
  },
  scope: "self" | "neighbor" | "pair", // на кого смотрим/влияем
  then: [ {op:"split", into:["C1","C1"]},
          {op:"setTag", tag:"пар"},
          {op:"addAttr", attr:"temp", delta:3} ],
  route: "out1"                        // на какой выходной порт (для splitter)
}

// Связь
Edge = { id:"e1", from:{node:"n3", port:"out0"}, to:{node:"n5", port:"in0"} }

// Граф целиком
Pipeline = {
  meta:{ name:"Конвейер воды", author:"...", version:1 },
  nodes:[...], edges:[...],
  globals:{ lambda:0.5, tickBudget:200 }   // λ как глобальный климат
}
```

**Набросок UI редактора:**

```
┌──────────────┬───────────────────────────────┬─────────────────┐
│  ПАЛИТРА     │           ХОЛСТ (граф)         │   ИНСПЕКТОР      │
│  узлов:      │                                │  узел: reactor  │
│ ▸ source     │   [src]──▶[filter]──▶[react]   │  rate: 1.0      │
│ ▸ reactor    │                    │           │  ── правила ──  │
│ ▸ filter     │                    ▼           │  IF class<=C2   │
│ ▸ merger     │                  [sink]        │     AND q==+    │
│ ▸ splitter   │                                │  THEN split→2×C1│
│ ▸ sink       │   [▶ Предпросмотр] [💾] [📂]   │  [+ правило]    │
│ ── пресеты ──│                                │                 │
└──────────────┴───────────────────────────────┴─────────────────┘
```

Взаимодействие: drag узла из палитры на холст → тянем связь от out-порта к in-порту → клик по узлу → в инспекторе строим IF/THEN из выпадающих списков (атрибут / оператор / значение / эффект). Кнопка «Предпросмотр» гоняет тестовый поток и **подсвечивает путь каскада** на холсте.

**Переиспользование существующего движка и геометрии:**

- Узел `reactor` **не пишет физику заново** — он вызывает уже существующие `split()`/`merge()` инфонов; новизна только в том, что *условие/параметры* берутся из правила, а не из глобального λ.
- `source`/`sink` опираются на текущую «станцию встреч» (06.7): источник = спавнер, приёмник = та же логика поглощения/очереди.
- `pos` узла мапится на **существующую гибридную геометрию**: орбиты = «магистрали» (длинные трубы между классами), лепестки цветка жизни = «реакторные слоты», метро-схема = упрощённый граф-вид. То есть редактор рисует поверх той же координатной системы, что и игра.
- Исходы встречи (обмен/слияние/отталкивание/очередь) становятся **встроенными пресетами реактора** — игрок не изобретает их с нуля, а берёт готовыми и докручивает.

### 4. Поэтапный план реализации

| Фаза | Содержание | Критерий готовности (Definition of Done) |
|---|---|---|
| **F0. Данные** | Ввести структуры `Node/Edge/Rule/Pipeline`; интерпретатор графа поверх текущего движка | Хардкод-граф `source→reactor→sink` гоняется в симуляции, инфоны реально делятся |
| **F1. MVP-редактор** | Холст, drag узлов из палитры, тянущиеся связи, 4 типа узла (src/filter/reactor/sink), 1 правило/узел | Игрок мышью собирает линейную цепочку и жмёт «Запуск» — поток идёт |
| **F2. Инспектор правил** | Таблица IF/THEN (атрибут/оператор/значение/эффект) из списков; атомарные правила | Можно задать `IF class<=C2 THEN split` без кода |
| **F3. Средний уровень** | `merger`/`splitter`, несколько правил на узел (приоритет), атрибуты `tags/temp/affinity`, влияние на соседа | Воспроизводится каскад «вода+огонь→пар» из 3+ узлов |
| **F4. Сохранение/пресеты** | JSON ↔ localStorage, библиотека пресетов, экспорт/импорт строки | Граф сохраняется, перезагружается, шарится файлом |
| **F5. Предпросмотр и защита** | Подсветка каскада, `tickBudget`/затухание, индикатор зацикливания | Петля не вешает вкладку; видно, какой узел «горит» |
| **F6. Сценарии/моды** | Уровни (src+цель sink+бюджет узлов), проверка решения, публикация графа | Уровень «собери C0→C3» проходится и автопроверяется |

Рекомендация: F0–F2 — это уже играбельный «мини-Factorio смысла»; средний уровень (F3) — там, где появляется обещанная заказчику **разнотипность и цепная реакция**; редактор как продукт «закрывается» на F4–F5.

### 5. Плюсы и минусы введения редактора

**Плюсы:**
- **Мощь выразительности**: из однотипных инфонов рождается комбинаторно богатое поведение без нового кода.
- **Реиграбельность и UGC**: игрок строит/делится конвейерами → бесконечный контент, моды, сообщество.
- **Совпадение формы и темы**: «конструирование смысла» буквально становится механикой — игрок крутит тот самый «рычаг смысла».
- **Переиспользование движка**: реактор = обёртка над готовыми `split/merge`, риск низкий, инкремент дешёвый.
- **Обучающий потенциал**: уровни-головоломки естественно вырастают из той же модели (цель = выходной инфон).

**Минусы:**
- **Кривая обучения**: node-graph + IF/THEN отпугивает казуального игрока → нужен онбординг, пресеты, режим «из коробки».
- **Баланс**: открытые правила ломают экономику замкнутой системы (фарм массы петлёй) → обязательны лимиты `tickBudget`, затухание, сохранение масс-баланса.
- **Производительность**: каскады + соседский поиск = O(N²) на встречах → нужен пространственный индекс (грид/quadtree) и потолок частиц.
- **Сложность реализации**: редактор (DnD, сериализация, предпросмотр) — отдельный крупный модуль, сопоставимый по объёму с самой игрой.
- **Риск «пустого холста»**: свобода без целей демотивирует → спасает связка с сценарными уровнями (F6).

**Вывод:** двигаться строго инкрементально — сначала интерпретатор графа поверх **существующих** `split/merge` (F0) и MVP-холст (F1–F2); разнотипность частиц и цепные реакции включать на F3, когда базовый конвейер уже стабилен; редактор-продукт с UGC — на F4+. Так каждый шаг остаётся играбельным и проверяемым, а риск по балансу и перфу гасится лимитами и пространственным индексом.

## Сводные плюсы/минусы, риски и рекомендация

Этот раздел сводит три возможные стратегии развития инфонов в единую картину «цена/польза», вскрывает системные риски перехода от однотипных частиц к семантическому конвейеру и даёт пошаговый маршрут от текущего прототипа (класс `lv`, масса `m`, иногда заряд `q`) к редактору правил.

### Три стратегии: краткие определения

| Код | Стратегия | Суть в одной строке | Что меняется в инфоне |
|---|---|---|---|
| **A** | Простые/однотипные | Оставить как сейчас: различие только по `lv`, `m`, иногда `q` | Ничего |
| **B** | Богатые атрибуты + формульные правила | Вектор атрибутов + условные правила реакций (цепные каскады), но правила **захардкожены** в коде/конфиге | `{lv, m, q, вектор семантики, полярности, теги}` |
| **C** | Полный семантический конвейер | То же, что B, плюс **редактор правил** для игрока и сборка пайплайнов «примитив → продукт» | То же + правила как данные, доступные игроку |

### Сводная таблица сравнения

Шкала: ★ (низко/слабо) … ★★★★★ (высоко/сильно). Для «сложности», «риска дисбаланса» и «порога входа» больше звёзд = **хуже**.

| Критерий | A: простые | B: атрибуты+формулы | C: конвейер+редактор |
|---|---|---|---|
| **Выразительность** (что можно выразить смыслом) | ★★ | ★★★★ | ★★★★★ |
| **Эмерджентность** (неожиданное поведение) | ★★ | ★★★★ | ★★★★★ |
| **Сложность разработки** | ★ | ★★★ | ★★★★★ |
| **Производительность** (при больших N) | ★★★★★ | ★★★ | ★★ |
| **Риск дисбаланса** | ★★ | ★★★★ | ★★★★★ |
| **Порог входа игрока** | ★ | ★★★ | ★★★★★ |
| **Реиграбельность** | ★★ | ★★★★ | ★★★★★ |

Ключевое наблюдение: при движении A→B→C **польза (верх таблицы) и цена (низ таблицы) растут синхронно**. Нет «бесплатного» скачка. Это значит: нельзя прыгать сразу в C — иначе цена (сложность, дисбаланс, порог входа) ударит раньше, чем игрок успеет оценить пользу.

### Где «точка максимума» по аналогии с M(λ)

Здесь работает та же логика, что и в ядре концепции `M(λ)=4λ(1−λ)`: смысл живёт **между** полюсами.

- **A** — это полюс λ→0 в смысле дизайна: всё дробно-однотипно, мало смысла рождается из взаимодействий.
- **C без меры** — полюс λ→1: всё слишком связано, каскады сливают систему в одно состояние, игрок тонет.
- **B и аккуратно дозированный C** — это область λ≈0.5, где `M` максимальна: достаточно разнообразия для эмерджентности, но ещё управляемо.

Дизайн-вывод: целиться нужно не в «максимум функций», а в **максимум живого смысла на единицу сложности** — то есть в зону B с заделом под C.

### Главные риски и митигация

#### Риск 1. Комбинаторный взрыв правил
При `K` атрибутах и `T` тегах число потенциальных условий реакции растёт как ~`O(T² · 2^K)`. Уже при 6 тегах и 5 бинарных атрибутах — тысячи комбинаций, которые невозможно ни сбалансировать, ни протестировать.

Митигация:
- Правила задавать **не перечислением пар, а формулой** над атрибутами: один скалярный «потенциал реакции» `R = f(совместимость, заряды, полярности)` и пороги на нём. Тогда добавление атрибута не множит правила, а добавляет слагаемое.
- Ограничить число «активных» атрибутов на старте (3–4), остальные вводить волнами.
- Ввести **типы реакций как небольшой замкнутый набор** (split / merge / обмен / отталкивание / катализ), а атрибуты лишь выбирают исход и его силу.

Плюсы формульного подхода: масштабируется, читаем, поддаётся балансу одной кривой. Минусы: формула менее «интуитивна» для дизайнера, чем явная таблица пар.

#### Риск 2. Неуправляемые каскады → свал в полюс
Цепная реакция без демпфера почти всегда сходится к одному из полюсов: либо всё раздробилось в C0-шум (λ→0), либо всё слилось в одно C5-ядро (λ→1). В обоих случаях игра «умирает» — `M` падает к нулю.

Митигация:
- **Закон сохранения** уже есть (замкнутая система, масса делится/суммируется) — использовать его как естественный тормоз.
- Ввести **стоимость/охлаждение реакции**: каждая реакция тратит ресурс или повышает локальную «температуру», временно блокируя соседние — это обрывает лавину.
- **Глобальный гомеостат**: мягко тянуть λ обратно к 0.5 (отрицательная обратная связь), чтобы система не залипала в полюсе. Сила возврата — настраиваемый параметр сложности.
- Ограничить **длину каскада за тик** (например, не более `D` поколений распространения), остаток переносить на следующий тик — это и перф спасает, и зрелищность даёт.

#### Риск 3. Производительность при N частиц
Наивная проверка всех пар — `O(N²)` на тик. С каскадами и формулами на каждой паре это убивает кадр уже на сотнях частиц.

Митигация:
- **Пространственное хеширование / грид**: реакции только между соседями → `O(N)` в среднем.
- Реакции считать **на «станциях встреч»** (как в 06.7), а не глобально — это уже естественный пространственный фильтр.
- **Бюджет реакций на тик** (cap): лишние события — в очередь.
- Формулу реакции держать дешёвой (скаляр из 3–5 множителей), без ветвлений на горячем пути.

#### Риск 4. Перегруз игрока
Богатые атрибуты + редактор = когнитивная стена. Игрок видит вектор из 8 чисел и формулу — и закрывает игру.

Митигация:
- **Прогрессивное раскрытие**: на старте игрок видит 1–2 свойства, остальные «разблокируются» по мере прохождения.
- Атрибуты подавать **через метафору и цвет/форму** (полярность = цвет, класс = размер), а не голыми числами.
- Редактор давать **поздно и слоями**: сначала пресеты → потом «крутилки» параметров → потом полноценные формулы.
- Всегда иметь **рабочие дефолты**: игра должна быть играбельна вообще без захода в редактор.

### Чёткая рекомендация

Принцип «от простого к сложному» диктует: **не строить C сразу**, а пройти безопасный мост через B.

- **Минимальный безопасный шаг (перед углублением):** реализовать стратегию **B в усечённом виде** — добавить инфону **2–3 новых атрибута** (например, `полярность p ∈ [−1,1]`, `семантический тег s`, `сродство a`) и **одну формулу потенциала реакции** `R`, выбирающую исход на станции встреч. Без редактора, без длинных каскадов (глубина 1). Это малозатратно, обратимо и сразу проверяет главную гипотезу заказчика: «возникает ли семантическая цепная реакция».
- **Следующий шаг:** включить **короткие каскады (глубина 2–3)** с демпфером (охлаждение + гомеостат λ), добавить ещё 2–3 атрибута волной, отладить баланс на одной кривой `R`. Это полноценная стратегия **B**.

> **Статус переноса в p78.** `prototype/lib/semantic-reaction-rules.js` теперь является единым версионированным каталогом `R_SYNTH / R_FRAGMENT / R_CATALYZE / R_MEDIATE / R_HOMEOSTASIS` для обоих причинных слоёв. Каталог задаёт приоритет, стоимость, направление, входной/выходной порт и `pre/inv/post/proof`; событие несёт `ruleVersion`, `ruleHash` и проверяется каталогом. `prototype/lib/semantic-reaction-field.js` строит детерминированный структурный прогноз по токен-графу, а `prototype/lib/semantic-reaction-runtime.js` отдельно исполняет наблюдаемые встречи движущихся частиц в нормированных координатах `x/y`: Cartesian spatial hash, точная ревизия и последовательный logical tick, глобальный арбитраж кандидатов, cooldown, лимиты пар/кандидатов/событий/каскада, причинные `eventId/parentEventId` и пакетное применение эффектов из неизменяемого pre-state. Реакции разрешены только между разными токенами; масса сохраняется, `0.18<u<0.82`, глубина не выше трёх. GUI явно разделяет `FORECAST` и `OBSERVED`. Runtime по-прежнему меняет только состояние частиц и сам не записывает текст; `text-result.js` читает его snapshot и строит отдельную read-only строку наблюдения и пункт меню вывода. Граница остаётся `STRUCTURAL / NOT_COMPUTED`: это ещё не редактор стратегии C и не доказательство смысловой истинности.
> **Локальная причинность p78.** Выбор реакции теперь задан отдельной детерминированной политикой `rule = P(mode, source.type, target.type, relation)`. Явное «обобщить» или «уточнить» переопределяет локальные типы; в обычном `orbit` частица `seed/catalyst` передаёт ход, `synth` двигает цель к обобщению, `fragment` — к детализации, конфликт в `repair` вызывает посредничество. Знак `Δu` вычисляется из `rule.direction`, поэтому один каскад может содержать разные направления. Событие сохраняет нормализованный `selectionInput` и `selectionReason`; каталог повторно вычисляет выбор и отвергает подмену правила или причины. `FORECAST`, `OBSERVED` и текстовый вывод показывают причины и накопленные счётчики `generalize/detail/orbit/repair`.
> **Калибровка FORECAST ↔ OBSERVED.** Runtime строит целевой профиль `T`: для явных `generalize/detail` соответствующее направление получает 100%; в остальных режимах `T = 0.75 × forecastMix + 0.25 × particleTypeMix`. Наблюдаемое расхождение — total variation `Δmix = 1/2 Σ_d |O_d − T_d|`. Накопленный долг направления равен `debt_d = clamp(T_d × n − count_d, −1, 1)`; он ограниченно меняет только уже допустимого кандидата: `F' = F × (1 + 0.12 × score)`, `priority' = priority + 20 × score`. One-step handoff учитывает тип цели с весом 0.3, только если после её активации остаётся разрешённое поколение. Каталог, локальный `selectionReason`, порог, one-touch, масса и `0.18<u<0.82` не меняются. Если нужного пространственного соседа нет, событие не создаётся искусственно: `Δmix` остаётся видимым расхождением, а не скрывается подгонкой.
> **Профиль пространственных возможностей.** `Δmix` теперь раскладывается на причину. Opportunity учитывает только гетерогенную пару `active source → idle target`, попавшую в радиус и прошедшую эффективный порог. Текущие действия и generation-aware handoff считаются раздельно в bounded EWMA-окне `C_t = 0.92 C_(t−1) + eligible_t`. Доступная смесь `A = 0.7 × currentOpportunity + 0.3 × handoffOpportunity`. Интерфейс показывает `Δmix = TV(O,T)`, `Δspace = TV(A,T)` и `Δcontrol = TV(O,A)`. Большой `Δspace` означает, что нужных встреч не дала геометрия; большой `Δcontrol` — что арбитраж плохо использовал доступные встречи. Это запрещает приписывать движку смысловую ошибку там, где направление физически отсутствовало.
> **Бюджет плавности p78.** Логический runtime больше не вызывается из каждого физического `step()`: он запускается по экранным кадрам через idle-очередь и не зависит от значения темпа. Визуальный темп теперь интегрируется максимум двумя масштабированными подшагами: при значении `9` выполняются два прохода по 180 частицам с `stepScale=4.5`, а не девять полных проходов. Экспоненциальный boundary gain `1−0.65^stepScale` сохраняет устойчивое возвращение в `0.18<u<0.82`. Жидкий слой ограничен шестью полосами по 72 сегмента; spatial runtime по-прежнему обрабатывает детерминированную выборку 96 частиц со всеми токенами. DOM-панель обновляется через idle-очередь раз в 24 кадра. Canvas раздельно публикует `simulationMs`, `drawMs`, `frameWorkMs`, `runtimeMs` и число подшагов. На localhost при темпе `9` измеренная работа кадра после изменения составила около `4.3 ms` (`0.3 ms` симуляция, `4.0 ms` рисование, два подшага); редкие большие интервалы между `requestAnimationFrame` остаются отдельным свойством встроенной оболочки и не смешиваются со стоимостью алгоритма.
> **Причинное текстовое продолжение p78.** `prototype/lib/semantic-trace-continuation.js` восстанавливает последний наблюдаемый суффикс по `eventId/parentEventId`; если наблюдаемых событий ещё нет, использует детерминированную цепь `FORECAST`. Формула слоя: `continuation = Template(genre, effectiveDirection, witnesses(trace,input))`, где handoff-направление применяется только при зафиксированном `handoff:underrepresented`, иначе берётся направление последнего события. Для `READY` нужны не менее четырёх содержательных токенов, три разных свидетеля `topic/bridge/detail` и хотя бы один свидетель из trace. Короткий ввод, пустая цепь, `BLOCKED`, выход из `0.18<u<0.82` или неполный набор свидетелей дают явный `ABSTAIN` без строки вставки. `OBSERVED` не подменяется прогнозом после ошибки. Шаблон хранит хеши входа/trace/выхода, но честно остаётся `STRUCTURAL / NOT_COMPUTED`: воспроизводимость причинной привязки не является доказательством смысловой истинности.
> **Графический causal overlay p78.** `prototype/lib/semantic-trace-view.js` не рассчитывает новый смысл, а проецирует тот же continuation-pack на движущиеся `drops`: для `OBSERVED` сначала используется точный `sourceId/targetId`, для `FORECAST` — сохранённый `tokenIndex`. Три разных частицы получают маркеры `Т/М/Д`, причинный путь рисуется сплошным для факта и пунктирным для прогноза, а слова вынесены в одну нижнюю легенду, чтобы не перегружать кольцо. `READY` требует `3/3` mapped witnesses и хотя бы одно ребро; неполное сопоставление честно становится `PARTIAL`, `ABSTAIN` рисует только статус. Overlay пересобирается вместе с текстовым результатом, на кадре читает O(1)-lookup по `drop.id` и публикует `data-trace-status/origin/witnesses/edges/hash` для автоматической проверки.
> **Контрфактический параметр p78.** `semantic-parameter-counterfactual.js` рассчитывает три прогноза над одним неизменяемым текстом, целью и анализом: `CF(λ,δ)=FORECAST(text, λ−δ | λ | λ+δ) → compare(status, traceHash, direction, events, ringMargin)`, по умолчанию `δ=0.12`. Это только `FORECAST`: слой не приписывает альтернативам наблюдаемое происхождение и не меняет текст или частицы. `STABLE` означает одинаковые READY-trace и направление у соседей, `SENSITIVE` — изменение хотя бы одного соседа при READY-базе, `ABSTAIN` — отсутствие READY у текущего λ. Пассивная панель показывает `M(λ)`, число событий, диапазон `u`, `Δg`, направление и trace relation для `λ−/λ/λ+`; у неё нет кнопок или обхода action gate. Все выводы остаются `STRUCTURAL / NOT_COMPUTED`.
- **Конечный ориентир:** **стратегия C** — вынести правила в данные и дать игроку **редактор слоями** (пресеты → параметры → формулы) и сборку «семантического конвейера» примитив→продукт. Переходить сюда только после того, как B показала живой, сбалансированный геймплей.

Обоснование: B даёт ~80% выразительности и эмерджентности от C при существенно меньшей цене по сложности, балансу и порогу входа. Это и есть «зона максимума `M`» в пространстве дизайн-решений.

### Чек-лист «что делать дальше» (по шагам)

1. **Зафиксировать модель атрибутов**: расширить инфон до `{lv, m, q, p (полярность), s (тег), a (сродство)}`; задать дефолты, чтобы старая логика не сломалась.
2. **Ввести единую формулу потенциала реакции** `R = w₁·совместимость(s) + w₂·(qᵢ·qⱼ) + w₃·(pᵢ·pⱼ)` с порогами на исходы (слияние / обмен / отталкивание).
3. **Подключить `R` к станции встреч (06.7)** вместо текущей логики «заряд+близость классов»; каскад пока глубина 1.
4. **Прогнать тест гипотезы**: видна ли осмысленная разнотипность и хотя бы один интересный исход? Если нет — крутить веса `w`, а не усложнять.
5. **Включить короткие каскады (глубина 2–3)** + демпфер: охлаждение реакции и мягкий возврат λ→0.5.
6. **Добавить перф-защиту**: пространственный грид + бюджет реакций на тик.
7. **Расширить атрибуты второй волной** (ещё 2–3) и сбалансировать одной кривой `R`.
8. **Вынести правила в данные** (JSON/таблица), чтобы код их только исполнял — это фундамент редактора.
9. **Дать редактор слоями**: сначала пресеты, потом параметры-«крутилки», потом формулы.
10. **Собрать первый «семантический конвейер»** примитив→средний продукт как демонстрацию C и точку входа в реиграбельность.

Короткий итог: **начать с B-усечённого (шаги 1–4) как минимального безопасного шага, развить до полного B (5–7), и только затем строить C с редактором (8–10).** Это сохраняет систему в «живой» зоне между полюсами и не даёт цене обогнать пользу.

## Решение для заказчика (резюме)

- **Частицы сейчас — почти однотипные** (`lv`, `m`, иногда `q`), поведением управляет глобальный λ. Этого достаточно для демонстрации рычага, но не для «цепной семантической реакции».
- **Да, можно ввести полярность/условия/формулы.** Предложена модель: вектор атрибутов + единая формула потенциала реакции `R` + продукционные правила «условие→эффект», из которых рождаются 4 типа каскада, управляемые λ и тормозами.
- **Семантический конвейер** строится лестницей: примитивы (1 правило/узел) → средний уровень (рецепты, ветвления, катализ) → редактор (гибрид граф + таблица IF/THEN) → моды/уровни.
- **Рекомендация:** идти **A → B(усечённый) → B(полный) → C**, по одному атрибуту за итерацию, каждый обязан быть *виден* в поведении. Минимальный безопасный первый шаг — шаги 1–4 чек-листа (полярность+тег+формула R на станции встреч, каскад глубины 1).

**Дальше по запросу:** реализовать шаги 1–4 как прототип («семантическая станция» с атрибутами и формулой R) → затем короткие каскады → затем MVP-конвейер/редактор. А также отложенные пункты: ретрофит звука/рекордов в остальные игры и новые жанры/сочетания.
> **Локальное корпусное свидетельство p78.** prototype/lib/semantic-data-evidence.js подключает vectors.json, phi_calibration.json и adaptive_k.json как отдельный read-only канал. Формула ранжирования ветви теперь имеет два явно разделённых слоя: structuralScore остаётся основным, а при DATA=READY применяется score = 0.95 × structuralScore + 0.05 × corpusScore. Корпус не меняет guard, не обходит DSL/transaction/action gate и при OOV возвращает ABSTAIN; без загрузки данных score = structuralScore. K=3 управляет только числом ближайших опор, а калибровочные пороги пока публикуются как provenance. Граница доказательности: LOCAL_CORPUS / NOT_COMPUTED, потому что 13 TF-IDF-опор не являются универсальной семантикой.
