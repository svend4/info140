## 1. Короткий вывод

### 1.3. Главный риск

Главный риск — не отсутствие идей и не качество кода. Главный риск — **замкнутый самоподтверждающийся контур**: лексикон → шаблоны → корпус → ожидания тестов → зелёный прогон. Внутри него:

- «ремонт» конфликта и центра регистрирует собственные ключевые слова как улучшение (находка A2-02, **critical**: регулярное выражение `hasMediation` ищет фразу «не сталкиваются напрямую», которую дописывает сам шаблон `executePortal`);
- охранные вердикты не отличают бессмыслицу от текста («фыва олдж ячсм итьбю» → `safe 0.79`, Φ `continue`);
- содержательные проверки транзакции не провалились ни разу, потому что кандидаты — 4–5 шаблонов, гарантирующих их прохождение;
- главный интерактивный путь «вставить ход» ломается на тривиальном вводе (перевод строки в конце текста → ложный `TX_STALE_SOURCE`), и это осталось незамеченным, потому что runtime не исполняется тестами.

Две из трёх блокирующих поломок исправляются одной строкой каждая.

### 1.4. Главный следующий шаг

Не новый слой и не новая спецификация, а **разрыв контура**: (1) два однострочных исправления и первый исполняемый сквозной тест оболочки; (2) `package.json` + CI с Chromium — чтобы «ALL PASS на машине автора» стало воспроизводимым фактом; (3) один живой документ-решение с чекбоксами вместо двенадцати дорожных карт; (4) детерминированная морфология и корпус D1 из собственных документов проекта, измеряемые уже существующим holdout-эвалуатором. Подробно — §7–8.

## 2. Методика и границы аудита

### 2.1. Как проводился аудит

Аудит выполнен в три этапа, каждый — как многоагентный рабочий процесс с обязательной состязательной верификацией:

| Этап | Состав | Результат |
|---|---|---|
| **Технический** | 8 аудиторов по зонам кода (runtime и оболочка; семантическое ядро и реакции; решение/транзакции/текст; Controlled Russian и Claim AST; evidence-слой; формулы/поиск/поток; тесты; инфраструктура, прототипы и данные) → 8 скептиков-верификаторов, обязанных открыть каждый указанный файл и строку и по умолчанию отклонять неподтверждённое → консолидация | 107 находок, **106 подтверждено, 1 отклонено** (сверхлинейная стоимость replay не воспроизвелась: рост линейный, бюджеты срабатывают раньше таймаута); после слияния дубликатов — 59 находок в 7 темах |
| **Концептуальный** | 5 читателей документации (00–08 + диаграммы; 09–19; 20–29; 30–41; 42–52) с обязательной сверкой утверждений документов с кодом → 3 сквозных аудитора (когерентность терминологии; научная честность; стратегия и конвергенция) → 8 скептиков → консолидация | 95 находок, **95 подтверждено, 0 отклонено** |
| **Пути развития** | 7 независимых углов идеации (научный инструмент; продукт; гибрид с языковыми моделями; формальные методы; опыт и игра; радикальные идеи; обрезка и управление) → 3 независимых судьи с разными акцентами → синтез программы → критик полноты → заполнение пробелов | §7–8 |

Всего в аудите участвовало более 45 агентов, выполнено около тысячи обращений к файлам и командам.

### 2.2. Что запускалось

- `node prototype/tests/run-all.cjs` — трижды, на Node v22.22.0 (Linux): **ALL PASS, suites 61/61, checks 775/775**, 42–47 с.

В оригинальном виде на Linux оба падают до первой проверки («Chromium distribution 'msedge' is not found»).
- Независимый smoke всех 80 прототипов с заблокированными внешними хостами: 78/80 без ошибок консоли; p6 и p60 требуют cdnjs.
- Smoke P78 под Chromium (два независимых прогона): загрузка 1.7–1.8 с, 67 скриптов (1.3 МБ), 60 FPS, 0 ошибок консоли, 0 long tasks, статус данных `READY`, нет горизонтальной прокрутки при 1360 и 390 px.

- Мутационный эксперимент в изолированном git worktree: 5 намеренных мутаций порогов и правил, полный прогон после каждой, затем `git checkout` — поймано **2 из 5** (0 из 3 в `semantic-core.js`).

### 2.3. Ограничения

- Автор не опрашивался; история решений восстанавливалась по датам внутри документов (git содержит два коммита одного дня).
- Человеческая разметка не проводилась; все оценки качества семантики — по поведению кода на зондах и по собственному holdout проекта.
- Агентный аудит может ошибаться в деталях формулировок; поэтому каждая находка прошла независимую проверку вторым агентом, а ключевые (§1.3, §5.3) — третий, ручной прогон. Там, где воспроизведение не удалось, это сказано явно (§9.4).
- Аудит не оценивает художественную и образовательную ценность 77 ранних прототипов; они рассматриваются как архив идей, что соответствует README проекта.

Из 2.45 МБ документации в исполняемом коде P78 живёт компактное и непротиворечивое ядро. Именно его стоит сохранять при любом развитии; всё остальное — либо метафора, либо план.

### 4.2. Терминология: один символ — много ролей

Концепция проекта не когерентна на уровне понятий, хотя дисциплинирована на уровне кода. Пять главных перегрузок:

**λ.** Прошлый аудит (docs/20 §5.3) насчитал восемь ролей символа λ и предупредил о тавтологии. Сверх них λ — свойство связи (docs/11:117), среднее трёх оценок (docs/11:319), центр масс распределения (docs/08:117), «рычаг через K» (docs/17:42), функция α (docs/16:198). В коде P78 при этом λ влияет только на (а) множитель `4λ(1−λ)` силы реакции, (б) слабый радиальный дрейф частиц (`runtime:1504`, `lever=(.5−lam)·.00072`), (в) число на панели и (г) вход `ring.balance` формульного адаптера. **Выбор текстовых операций от λ не зависит** — что docs/20 §5.4 уже констатировал, и что с тех пор не изменилось. Тезис «один рычаг управляет всем» вычислительно не замкнут.

**Ориентация шкал.** Код задаёт: λ↑ тянет к центру, центр = `u→0` = «3D-схлопывание» (`semantic-core.js:268`, `runtime:1985`), то есть λ ≈ 1−u. Документ docs/32:30 утверждает «u = λ», и runtime действительно передаёт λ в формульный адаптер как `u` (`runtime:504`) — ошибка скрыта лишь симметрией `4u(1−u)`. Сверх λ и u существуют ещё две шкалы «обобщение ↔ дробление»: α ∈ [−4, +4] (docs/45) и `x_rail` коридора (docs/52), причём docs/45 §9.1 прямо запрещает формулу λ↔α, а docs/16:198 признаёт λ = 0.5 + 0.095·α «по построению». **Четыре шкалы без утверждённой таблицы знаков.**

**1D / 2D / 3D / 2.5D.** Один токен обозначает пять вещей: размерность рендера игровых вариантов (docs/00, 05: «2.5D = псевдо-3D флагмана»), семантическую способность, где 3D = иерархия и это хорошо (docs/01:191), запретный полюс схлопывания (docs/45:35, `semantic-core.js:296`), соседнюю вкладку-интерфейс (docs/26:29: «1D = лента p79») и текстовый режим коридора (docs/52:13–21, с оговоркой «не заявления о размерности»). Одно из значений прямо инвертировано относительно другого.

**Φ и «живость».** Φ означает набор фаз метро (docs/04:77), здоровье флагмана `4λ(1−λ)·popFactor` (p4:89), произведение трёх факторов (docs/05:70), траекторную витальность `⟨M⟩·avg(g·N·κ)·κ_end` (docs/12, 15) и `sqrt(growth·novelty·openness·balance)` в runtime (`semantic-core.js:755, 786`) плюс две записи реестра (`vitality.snapshot-geomean`, `vitality.trajectory`). При этом **docs/12 §2 (строка 47) отвергает именно мультипликативную агрегацию, которая реализована.** «Живость» считается тремя формулами: `M(λ)` на панели, `life` в двух вариантах (`semantic-core.js:166` и `runtime:190`), `vitality` реестра. Вопрос docs/20 §5.5 «какая Φ каноническая» не закрыт.

**Границы «живой зоны».** Не менее семи несогласованных констант: `(0.06, 0.94)` clamp (`semantic-core.js:265`), `(0.18, 0.82)` зона риска (`:268–269`), `(0.181, 0.819)` ядро реакций, `0.055/0.945` «гибель» (`runtime:1518, 1523`), `0.12/0.88` dead-гейт p32, ползунки `0.02–0.98` (p4) и `1–99` (HTML), `lever_eps 0.02` (docs/06). Функция `clamp_open`, обещанная глоссарием docs/00:150 как «гарантия λ ∈ (0,1)», в коде не существует; псевдокод docs/06:337–339 объявляет её строго открытой, но реализует закрытый `clamp`.

**Глоссарий против кода.** Глоссарий docs/00 описывает архивный Проход 1: ≈20 терминов (`clamp_open`, `balance_flows`, `edge_cost`, `check_invariants`, `U_core/U_bound/U_flow`, T½, I2/I4/I5, Цветок жизни…) не имеют соответствия в P78; слово «инфон» в `p78-living-ring-interface.html` и runtime не встречается ни разу; валентность, спин, плотность и баланс тихо сменили значение (валентность: число связей → глагольные рамки; спин: ориентация → угловой инкремент; плотность: трафик → `tokens/14`). Действующие величины (`u`, `life`, `move`, `guard`, `corridor`, α, `x/y`) в глоссарий не внесены.

Дополнительно в ранней дуге: три несовместимые нумерации оболочек (docs/02: n=1 — ядро; docs/03: n=1 — внешняя; docs/06, D5, код: 0 — центр); «пробка» приписана то полюсу дробления (docs/04, 07), то полюсу обобщения (docs/01, 03, 05, 52); центр — то запретная мёртвая зона (docs/03:62), то самый связный проходной узел (docs/04:144–146).

### 4.3. Фальсифицируемость

Центральный тезис — «оба полюса губительны, максимум осмысленности внутри» — **на текущем коде не фальсифицируем**:

- `M(λ) = λ(1−λ)` выводится из определений `D := 1−λ`, `C := λ` (docs/01 §8.2, строки 219–227); docs/16:236 сам признаёт: «теорема о полюсах циркулярна в текущем виде: Φ→0 на полюсах — аксиома dead-гейта, не вывод».
- В P78 полюса недостижимы по построению: дрейф от λ (≤ 0.00036 за тик) против возврата к 0.5 (≥ 0.0013 за тик) даёт `|u − 0.5| ≤ 0.13` при инерции по умолчанию; мягкое отражение на 0.18/0.82 и `innerClamp` ядра делают пороги `coreHits/edgeHits` (0.055/0.945) недостижимыми; тестов на них нет.
- Из пяти «фальсифицируемых следствий» docs/16 §9.2 запущено **ноль** (№1, №2, №4 заблокированы λ-эстиматором, №3 ждёт p69 без эмбеддингов, №5 судится ручными порогами).
- Из 34 экспериментов каталога docs/39 с условиями опровержения создано **ноль карточек** (§13).
- Единственная выполненная внешняя проверка — holdout docs/41 — дала отрицательный результат (0/9), и это **самый ценный научный результат проекта на сегодня**, потому что он честно зафиксирован.

λ-эстиматор, на который опирается любое утверждение о тексте, — это лексикон из 28 лемм и 76 алиасов (`semantic-core.js:33`), 8 ручных «измерений» (`:4`), 127 словоформ и 4 sense-леммы мини-морфологии (`semantic-language.js`), подстроковые «стемы» (`semantic-core.js:79–87`) и фолбэк сходства 0.62 для любой неизвестной пары (`:100`). Ни одно содержательное предсказание о тексте не проверяемо на таком эстиматоре.

### 4.6. Сильные стороны концепции

Аудит обязан быть справедливым, и здесь есть что отметить:

1. **Ядро идеи компактно и переносимо.** «Две пропасти по краям одного хребта», открытый интервал, одна формула — это работающий дизайн-примитив: 11 играбельных MVP из палитры docs/08 и p1–p6/p20 показывают, что рычаг между двумя смертями работает в ритме, merge-пазле, idle, zen и PvP.
2. **Методологическая самодисциплина, редкая для одноавторского проекта.** docs/16 вводит обязательную оговорку происхождения и пять уровней точности (ТОЖДЕСТВО / РОЛЬ / МЕТАФОРА / ПЛАН / ПО ПОСТРОЕНИЮ); docs/19 разводит теоремы и гипотезы и честно снимает соблазны (поворот ≠ хаос, φ не уникально, нормальность π не доказана); docs/14 находит дыры в собственном DSL; docs/33 аудирует собственный источник и понижает его преувеличения.
3. **Честный отрицательный результат.** docs/41 — физическое разделение input/gold, content-addressed seal, проверка отсутствия утечки эталона в runtime и HTML, публикация провала вместо ослабления порогов. Это единственная в проекте внешняя проверка, и проведена она правильно.
4. **Границы полномочий закреплены механизмом, а не текстом.** `semanticTruth:false`, `commitAllowed:false`, `soundness:NOT_COMPUTED`, запрет полей authority на уровне контракта, adversarial-тесты (fake hitId, rehashed forgery, TOCTOU-snapshot, stale worker).
5. **Цепочка 45→51 — воспроизводимый метод работы с внешней идеей:** pin commit → критический аудит (docs/43, 47) → независимая реализация → adversarial-тесты → подключение. Критика внешних источников содержательна там, где это математика (phase π/2 даёт параболу; LCI не измеряет замыкание; «2-opt» в p55 на деле pair swap).
6. **Поздние метафоры честно огорожены:** jamming помечен `diagnosticOnly`, Рамсей — «no local theorem is claimed» (`p78-marginal-corridor.js:275–280`), гидрология — «что не переносить» (docs/44 §15.13).

### 4.7. Консолидированный концептуальный вердикт

После слияния 95 подтверждённых находок в 22 (идентификаторы F-01…F-22, приложение B) ведущий концептуальный аудитор сформулировал вердикт, который здесь приводится без смягчения:

> Концептуально MERIDIAN/P78 находится на стадии богатой, внутренне продуманной модели-каркаса, у которой есть один настоящий вклад и одно настоящее доказательство — но не те, что заявлены в точках входа. Настоящий вклад идеи — не «рычаг смысла» и не M(λ), а **инженерная дисциплина честности**: content-addressed fail-closed контракты, в которых эвристика конструктивно не может быть повышена до истины, детерминированный replay с hash-seal, adversarial-тесты и публикация отрицательного holdout 0/9 вместо подгонки порогов. Это редкая и переносимая культура, которую стоит сохранить при любом развитии. Метафорой остаётся почти весь фундамент 01–08 и значительная часть поздних заимствований: инфоны и таблица Менделеева, Цветок жизни и бинду, логистика M/M/1, Рамсей, jamming, гидрология, девять α-орбит до подключения — они не порождают ни узлов, ни формул, ни тестов, а замкнутость кольца на деле задаётся двумя числами (0.18/0.82) и отражением. Недоказано главное: что M(λ) или любая из четырёх Φ измеряет осмысленность текста, что «одно правило» связывает пять систем, и что система способна показать хотя бы один поддержанный CONTINUE. Главный концептуальный риск — не ошибка, а подмена: проект измеряет прогресс числом зелёных проверок и объёмом спецификаций, а не сдвигом целевых исходов; «честный ABSTAIN на 100 % входов» становится неотличим от отсутствия функции, а зрелая инфраструктура остаётся верификатором без единого кандидата.

### 5.2. Подтверждённые дефекты: critical и high

Ниже — 11 находок уровня critical/high после слияния дубликатов (полный список из 59 — в приложении A). Каждая проверена вторым агентом по указанным строкам; четыре воспроизведены в §5.3 вручную.

#### A2-02 · CRITICAL · «Ремонт» самоисполняется: regex-гейты ядра ищут фразы, которые генерируют его же шаблоны

`hasMediation` (`semantic-core.js:126`) ищет в тексте `/связк|мост между|через[^.!?\n]{0,50}мост|не сталкиваются напрямую/`, а `executePortal` (`:247`) дописывает строку «Связка: «…» и «…» не сталкиваются напрямую; через «…» …». `counterIntent` (`:278`) ищет `/не\s+(сжимать|сжать|сверн|…)/`, а `balanceRepair` (`:316`) дописывает «Баланс: не сжимать все в одну точку; оставить пример…». Воспроизведено: «шум мешает смыслу» → `zone=conflict`; после добавления одного слова «связка» → `conflicts=0`, `zone=safe`. «сжать все в одно главное» → `center (0.24)`; после строки balanceRepair → `safe (0.81)`. На той же фразе `topic == fact`, и шаблон порождает «„обобщение“ проявляется через „обобщение“». Все ранжирования ветвей (balanceRepair, composeContinuation, backtrack, trajectory, Φ, goal) измеряют присутствие собственных ключевых слов, а не изменение структуры; тесты закрепляют это как норму. **Дефект проявляется на фиксированном корпусе проекта, то есть внутри заявленной области применимости** — цель REPAIR из docs/31 §16 не достигается даже на корпусе.
*Рекомендация:* убрать текстовые regex-гейты из оценки; медиацию считать структурно (наличие bridge-оператора между конфликтующими вершинами графа отношений); служебные префиксы «Связка:» / «Баланс:» исключать из повторного анализа; отрицательный тест «добавление слова „связка“ не меняет зону».

#### A2-01 · HIGH · Guard, Φ и реакционное поле не отличают бессмыслицу от текста

«фыва олдж ячсм итьбю» → `life 0.44`, `stabilityGuard safe/0.79`, Φ `continue`, реакционное поле `critical` с 3 срабатываниями и текстом «„фыва“ передает следующий ход к „итьбю“». Бытовое русское предложение вне словаря → `safe 0.81`, английское → `safe 0.64`, связный абзац → `0.92`: шкала почти не разделяет. Причина: `life` и `guard` — арифметика над долями ролей и длиной (`semantic-core.js:162, 166, 284`); при нулевом покрытии поле подставляет `sequence`-рёбра с фиксированными `score .62 / fit .72` (`semantic-reaction-field.js:109`). Единственный abstain (`clarify/low_coverage`) живёт в `semantic-decision` и не используется ядром, guard, Φ и полем.
*Рекомендация:* явный abstain-путь в `analyzeText/stabilityGuard/semanticPhi` при покрытии словарём ниже порога; не подставлять sequence-рёбра при нулевом покрытии; suite «guard honesty» с упорядочением «связный > повтор > мусор»; покрытие словарём как обязательный «знак доверия» рядом с каждым вердиктом.

#### A2-04 · HIGH · Роли назначаются подстрочным `indexOf` в обе стороны

`hasStem` (`semantic-core.js:79`) и сопоставление алиасов (`:82`, `w.indexOf(k)>=0 || k.indexOf(w)>=0`) дают систематические ложные роли: «условие» → «слово»/detail, «перекресток» → «река»/bridge, «картон» → «карта», «ключица» → «ключ», «система»/«математика» → core (через стем «тема»), «выход»/«расход»/«находка»/«животное» → bridge, «фактор»/«стратегия»/«анатомия» → detail; короткий токен «ре» совпадает с «рек» из-за обратного включения. Приоритет `detail > core > bridge` неявный (`:87`). Роли определяют `core/edge/move`, `u` и зону — на произвольном тексте «семантический радар» измеряет случайные вхождения подстрок.
*Рекомендация:* до морфоанализатора — префиксное сравнение с минимальной длиной стема и запретом обратного включения; затем сопоставление по лемме из общего `MorphologyProvider` (см. A4-01); понизить confidence для `match='stem'`.

#### A3-01 · HIGH · Необязательный чек блокирует транзакцию, причина отказа ложная

`semantic-decision.js:139` помечает `data_support` как `required:false` и исключает его из `structural` (`:140`), но `semantic-transaction.allVerificationChecksPass` (`:172`) требует `ok===true` у всех чеков без учёта флага. Воспроизведено верификатором на 19 фразах: модуль `semantic-data-evidence` загружен, данные не `READY` (окно до завершения `fetch`, любой сбой, `file://`) → **apply 0/19** с причиной `transaction_not_ready` и текстом «Транзакция не прошла pre/inv/post»; модуль отсутствует → 13/19; данные `READY` → 12/19. Пользователь видит «данные: UNAVAILABLE · влияние не более 5 %» (`runtime:877`) — сообщение не говорит, что вставка заблокирована. `prototype/README.md:3` допускает открытие напрямую, где `fetch` падает и блок становится постоянным.
*Рекомендация:* в `allVerificationChecksPass` пропускать чеки с `required===false`; сообщение транзакции должно называть провалившийся чек; регрессия «data-evidence загружен без данных → decide(рабочая фраза) === 'apply'». Исправление — одна строка.

#### A3-03 · HIGH · Ложный STALE на переводе строки

`decide()` хранит `trim`-нутый source (`semantic-decision.js:215`); `commitPrepared` и runtime передают сырой `condition.value` (`runtime:1041`); commit сравнивает полный текст (`semantic-transaction.js:470`). Воспроизведено: `evaluate(фраза+'\n')` → `READY/apply`; `commitPrepared(та же строка)` → `BLOCKED TX_STALE_SOURCE`, `changed=false`; с обрезанной строкой → `COMMITTED`. Пользователь, закончивший ввод клавишей Enter или вставивший текст с переводом строки, видит READY и получает STALE без изменений. Тесты не ловят, так как используют уже обрезанные строки.
*Рекомендация:* одна функция `canonicalSource` (trim + нормализация переводов строк) в `decide`, `evaluate`, `commitPrepared`, `commitLine`; тест «evaluate + commit на тексте с концевым \n». Исправление — одна строка.

#### A4-01 · HIGH · Морфологии нет, «швы» для морфоанализатора номинальны

Лексикон: 520 форм, 381 уникальная в нижнем регистре, 138 лемм; ≈3.5 формы на существительное из ≈12 падежно-числовых, ровно 3 на глагол. Пробы: «Частицы движутся по орбитам.» → `OOV(орбитам)`; «Частица двигалась по орбите.» → `PREDICATE_OOV`; «Частица будет двигаться по орбите.» → `OOV(будет)`; «Система избегает коллапса при обобщении.» → `OOV(обобщении)`. Разрешение только по точной поверхности (`p78-controlled-russian-lexicon.js:628`, `p78-linguistic-parser-adapter.js:65`, `matchMode:'EXACT'`); `search-contracts` допускает `LEMMA`, но `LocalTextIndex` его отвергает (`p78-local-text-index.js:278`); мини-морфология `semantic-language` парсером не потребляется. Документация честна (docs/35:215 «точные словарные формы»), внешний holdout (0/9) подтверждает нулевую переносимость. Переход к морфологии — не «подключение адаптера», а одновременный рефакторинг `matchPatternTemplate`, `predicateMatches`, `buildArguments`, валидатора корпуса и индекса с новыми `lexiconHash/patternSetHash`.
*Рекомендация:* контракт `MorphologyProvider {analyze(text) → tokens[{surface, lemma, pos, feats, offset}]}` с `providerRef` в `parserRef`; sense как лемма + парадигма; `resolveLemma` (`matchMode:'LEMMA'`) и LEMMA-нормализация в индексе; development-набор отдельно от blind holdout. Инновационный вариант: детерминированный словарь парадигм на 138 лемм, сгенерированный один раз из открытого морфословаря и захешированный — сохраняет content-addressing без внешней зависимости в рантайме.

#### A4-02 · HIGH · Парсер привязывает роли без проверки онтологии

`buildTemplateArguments` связывает слоты с токенами по индексу без `ontologyScore` (`p78-linguistic-parser-adapter.js:166`); matcher проверяет лишь наличие ролей (`p78-claim-structural-matcher.js:34`). Пробы: «Статья продолжает редактора.» → `RESOLVED`, `STRUCTURAL_MATCH claim.continue.positive` с `PROCESS = editor.person` при требуемом `PROCESS/TEXT`; «Контекст сохраняет система.» (OVS) → `AGENT = context`, `THEME = system`. Сквозной эффект: structure-index с пассажем «Контекст сохраняет система.» даёт `SUPPORTS` для цели «Контекст сохраняет систему.», а настоящий парафраз «Система сохраняет контекст.» получает лишь `MENTIONS`. В свободном пути при `ontologyScore = 0` позиционный бонус +3 проходит фильтр `score > 0` (`:93, :250`); сочинение «и» поглощается молча.
*Рекомендация:* требовать `ontologyScore > 0` для привязки (позиция — только tie-breaker); `ROLE_TYPE_MISMATCH / UNBOUND_TOKEN → AMBIGUOUS`; явная обработка сочинения; отрицательные фикстуры с нарушением типов.

#### A5-04 · HIGH · Пять строк эвристики под 5.5 тысячами строк контрактов

### 5.6. Тесты: что они защищают и чего нет

Тестовая система — лучшая часть инженерной инфраструктуры проекта и одновременно источник ложного ощущения покрытия.

| Что защищено | Что не защищено |
|---|---|
| детерминизм, hash-стабильность, replay в свежем VM (equality хешей) | семантическое поведение на тексте, не порождённом автором |
| fail-closed коды, неизменность контрактов, запрет DOM/clock/random/eval в ядрах | исполнение главного runtime (0 строк), p79/p80, мостов |

### 5.8. Сильные стороны кода

1. **Воспроизводимость без экосистемы:** 61/61, 775/775 на чистом Node без `npm install` — редкость для JS-проекта.
2. **Централизация изменений текста:** все записи `condition.value` проходят через `finishSemanticOutcome` / action-controller (`runtime:979, 1982`); план docs/23 §5 выполнен и покрыт исполняемыми проверками.

6. **Content-addressing реализован корректно:** собственный SHA-256 совпадает с эталонными векторами; канонизация отвергает суррогаты, NaN, циклы, accessors.
7. **Worker-протокол** с версионированием, подавлением устаревших ответов, таймаутом и `terminate` — UI-поток не блокируется replay.
8. **Браузерные тесты содержательно сильные** (canvas-хеши до/после, изоляция источника от соседних миров, overflow на 390 px) — нужно лишь снять привязку к Edge.
9. **Progressive disclosure** реализован: режим «ход» показывает 4 секции, 27 скрыты; клавиатурная навигация и `aria-pressed`.
10. **Честная деградация данных:** под `file://` P78 показывает `UNAVAILABLE` и продолжает работать (кроме A3-01).

### 7.1. Как устроен этот раздел и что в нём общего

Третья фаза аудита была устроена как состязание: семь независимых агентов-идеаторов (научный инструмент; продукт; гибрид с языковыми моделями; формальные методы; опыт и игра; радикальные направления; обрезка и управление) получили одну и ту же сводку аудита и обязаны были предложить пути, которые (а) закрывают конкретные находки, (б) не повторяют 34 идеи docs/39, ветви docs/44 и этапы docs/31 как новые, (в) **фальсифицируемы за четыре недели**. Три независимых судьи с разными акцентами (научная строгость; выполнимость и польза за 3 месяца; оригинальность и долгосрочный потенциал) оценили все 35 путей по шести критериям, после чего один агент-синтезатор собрал программу, а критик полноты проверил её на пробелы. Итог — §7.2 (каталог), §7.3 (рейтинг), §7.4 (программа), §8 (первый спринт, развилки, метрики).

Прежде чем перейти к каталогу, стоит назвать то, в чём сошлись семь независимых углов — это и есть самый надёжный вывод фазы:

1. **Сначала опровергнуть, потом строить.** Шесть путей из разных углов (1, 11, 17, 22, 27, 28) предлагают одно и то же первым шагом: проверить на существующих модулях, измеряет ли ядро хоть что-то, кроме собственных ключевых слов. Методы разные (абляция триггерных слов, подмена формы окна `M(λ)`, Монте-Карло достижимости полюсов, adversarial-корпус, предрегистрированная корреляция четырёх шкал, оценки людей на лестнице стимулов), вывод один: отрицательный результат — это deliverable, а не провал.
2. **Корпус и морфология — критический путь, и его можно начать из собственных документов.** Пути 2, 3, 6, 7, 13, 14, 35 сходятся на том, что D1-корпус не надо «где-то брать»: 107 тысяч слов docs/ содержат тысячи определений и — что ценнее — уже найденные аудитом противоречия, которые становятся первым gold. Морфология при этом «компилируется» в хешированную таблицу на этапе сборки, а не добавляется зависимостью в рантайм.
3. **Главный путь пользователя надо починить до любых экспериментов.** Однострочные исправления A3-03 и A3-01 входят первым пунктом в девять путей из семи углов (5, 9, 10, 12, 16, 18, 23, 31, 35). Без них любое измерение «инструмент против Ctrl+F» нечестно.

#### I1. Научный инструмент

Как превратить P78 в воспроизводимую исследовательскую установку с внешней валидацией. Общая логика угла: сначала проверить, измеряет ли ядро хоть что-то, затем сравнить его с тривиальными базлайнами, затем вынести бенчмарк наружу.

| № | Путь | Гор. / усилие | Суть | Как опровергнуть за 4 недели |
|---|---|---|---|---|

- **Один внешний человек на квартал.** «Четыре шкалы», «Два полюса», «Ctrl+F», «Три берега», RCC-pilot конкурируют за одного и того же внешнего участника, которого у проекта не было 14 месяцев.


### 7.4. Программа развития (синтез)

Синтез выполнен одним агентом поверх 35 путей, рейтинга и комментариев судей, затем проверен критиком полноты (его замечания и внесённые поправки — в §8.5). Программа **не является тринадцатой дорожной картой проекта**: по собственному правилу «ровно одна живая карта» она должна быть перенесена автором в короткий `docs/STATE.md` с чекбоксами (см. §8.1, задача 9), а настоящий документ — заморожен как снимок аудита. Всё ниже — предложение, а не решение.

#### 7.4.1. Рекомендуемая идентичность

> **Детерминированная лаборатория-верификатор русского текста под human review** в конфигурации «только 2D» (docs/31 §5.1: parser + claim graph + operators + evidence gate + selector + ledger), с ядром ветки A в форме Natural Definition Compiler (docs/44 §19, вариант 1) внутри минимальной оболочки ветки C: машина отвечает за кандидатов и обязательный контрпоиск, человек — за отношение с authority `HUMAN` в леджере (docs/44 §18.4: «C как оболочка, A как ядро, B позже»). Кольцо, коридор и Φ — проекция со статусом `ART_ONLY` до появления внешней корреляции.

Почему именно это, а не альтернативы docs/31 §5 и docs/44 §19: конфигурации с соседями (§5.2–5.4) допустимы только при измеримом улучшении, а Q6 сегодня — шесть `null`-флагов, 1D доказывает лишь побайтовую обратимость; «закрытое символическое кольцо» (вариант 2) — это то, чем проект стал де-факто (11 формул, 920 символов источников, 0 попаданий AST→grep), и оно запрещает заявлять произвольные тексты; «source-first conveyor» (вариант 3) — ветка B, самая дорогая, AG5 заблокирован до holdout v2; вариант 1 — единственный, для которого критический путь уже специфицирован (docs/42 §12, §25) и опирается на то, что код реально умеет (claim-ir, evidence-contracts, action-controller с CAS, ledger). Идентичность фиксируется как **гипотеза** (ADR-000) и проверяется измерением (исследование против Ctrl+F, misled-rate, триаж панелей по логам), а не декларацией в docs/00.

#### 7.4.2. Куда проект должен прийти за 12 месяцев

К октябрю 2027 MERIDIAN/P78 — клонируемый детерминированный верификатор русских утверждений под human review:

- `git clone && npm test` зелёный в CI на Linux/Chromium; главный runtime исполняется тестами, а не читается как текст (A7-01 закрыта);
- существует **один** запечатанный внешний артефакт — blind holdout v2 (цель ≥ 300 задач; реалистично 100–150 без второго аннотатора) с двойной человеческой разметкой, κ, data statement и лицензиями, на котором движок имеет ненулевой и честно опубликованный результат (ориентир: candidate recall ≥ 0.5 на development-срезе D1-b и ≥ 0.4 на v2 с интервалами Уилсона; macro-F1 публикуется при любом значении);
- морфология — скомпилированная хешированная таблица; естественные определения проецируются в DefinitionClaim; конфликт между определениями величин самого проекта (λ/u, «3D») находится машиной;
- один сценарий ценности (проверка абзаца против docs/ или собственной статьи автора) используется автором еженедельно и измерен против Ctrl+F;
- границы честны: `M(λ) = 4λ(1−λ)`, кольцо, коридор и Φ получают статус `ART_ONLY` или `MEASURED` только по результату предрегистрированных экспериментов; единственная возможная внешняя опора концепции — одна корреляция `|u − 0.5|` с оценками людей, опубликованная при любом знаке;
- языковая модель в продукте отсутствует, `semanticTruth` остаётся `false`; `CONTINUE` по docs/31 §16 либо впервые воспроизводимо выводится на D1 с квитанцией, либо записывается в STATE.md как недостижимый на текущем ядре;
- глоссарий — несколько именованных величин с привязкой файл:функция и знаком, измеренным на коде; ровно одна дорожная карта; единица движения — коммит с числом эвалуатора, а не документ.

### 8.2. Чего не делать

1. Не подключать кандидатов от языковой модели, REMOTE-провайдера, MCP-сервер или «Одну дверь» до AUC ≥ 0.8 на запечатанной adversarial-фикстуре с κ двух людей: сегодня `READY` означает наличие слова «Связка:», и «охраняемая генерация» будет упаковкой непроверенного гейта в продукт.
2. Не использовать silver-метки LLM-судьи как gold и не считать ИИ-ассистента вторым разметчиком для κ — иначе «blind» и «двойная разметка» docs/41 §10.5 становятся ложью.
3. Не создавать новых прототипов p81+, скинов, третьего режима интерфейса и визуальных слоёв до recall > 0 на D1-b: docs/20 это уже запретил, и через девять дней появились P79/P80.
4. Не плодить D1: ровно один корпус с одним владельцем, одной печатью, составом docs/41 §10.1 и разбиением D1-a/D1-b. Семейства источников development-пула и holdout-пула разделить заранее (`benchmark/FAMILIES.json`).
5. Не превышать два диагностических прогона запечатанного v1 за квартал (это **норма с журналом**, а не инвариант, который может проверить тест) и не расширять лексикон по ошибкам v1 (docs/41 §9).
6. Не принимать ADR о таблице знаков (λ против u, каноническая Φ) до измерения «Четырёх шкал»: зафиксировать знаки декретом перед sweep-ом значит повторить docs/32:30. Исключение — терминология «1D/2D/3D» и нумерация оболочек: это не знак шкалы, а коллизия имён, и её надо разрешить ADR уже на неделе 4 (различимые идентификаторы для рендера, способности, полюса, вкладки и режима коридора).
7. Не чинить гейты regex-чёрными списками или подбором под тот же корпус — только структурные исправления (членство леммы, зона `unknown`, проброс ABSTAIN) или sense-строки лексикона с replay-тестом, и проверка на замороженном корпусе раунда N в раунде N+1.
8. Не писать новых документов > 20 КБ без кода и не заводить тринадцатую дорожную карту: результаты идут в STATE.md, `experiments/RESULTS.md` и карточки ≤ 3 КБ; новый документ — только ADR ≤ 2 КБ, карточка или отчёт о реализации, привязанный к коммиту с кодом. **Это правило относится и к настоящему документу:** docs/53 — снимок аудита, а не источник полномочий для дорожной карты.
9. Не называть измерения теоремами, не заявлять «первый бенчмарк для русского» без сравнения с существующими наборами (TERRa, RuSuperGLUE, DaNetQA, русские наборы fact verification), не называть шесть поверхностных правил «линтером смысла».
10. Не смягчать условия фальсификации путей: пороги (κ < 0.2, flip-rate < 50 %, recall < 6/12, 0 решений, 0 коммитов) переносятся в карточки дословно, и каждый путь обязан уметь проиграть.
11. Не запускать хвосты ESM/Web Worker/d.ts, XL-карантин p1–p77 и три скина раньше результата четырёхнедельного маркера — это волна №13 под видом инфраструктуры.
12. Не запускать два эксперимента с людьми в один квартал и не начинать исследование с людьми, пока инструмент ничего не находит (recall 0 на D1) — иначе измеряется пустота.
13. Не заменять TF-IDF таблицей соседей и не включать «семантику» близости в UI до появления лемм и гейта полярности: дистрибутивные соседи тащат антонимы.

### 8.5. Что нашёл критик полноты, и как это учтено

Критик проверил программу на закрытие десяти технических приоритетов и ключевых концептуальных разрывов, на противоречия между путями и на завышенные обещания. Его вердикт — «не ok»: восемь пробелов, восемь противоречий, восемь overclaim. Четыре пробела были закрыты отдельными агентами; остальное внесено в текст выше как поправки. Полный список — здесь, потому что он сам по себе ценен как предупреждение.

**Пробелы (закрыты дополнениями):**

1. *План работы с людьми.* Пути 3, 11, 12, 13 упираются в «одного внешнего человека», которого не было 14 месяцев; в репозитории нет ни поля аннотатора, ни согласия, ни канала рекрутинга, а `judgeId` и логи сессий попадут в публичные фикстуры. Дополнение: `benchmark/HUMANS.md` ≤ 2 КБ с журналом обращений (три канала: платформа Prolific с prescreen «родной русский»; письмо на кафедру славистики немецкого университета; русскоязычные лингвистические сообщества) и датой первого обращения ≤ недели 2; форма согласия и псевдонимные `judgeId` без демографии; таблица «роль × часы × квартал»; **компенсация** (ориентир €15/ч; бюджет года ≈ €1 200) или честная альтернатива взаимной разметки; режим `humansMode: NONE | SINGLE | DOUBLE`, который читают пути. Автор находится в Германии — согласие и защита данных обязательны.
2. *Ёмкость автора и линия отсечения.* Дополнение: ADR-001 фиксирует два бюджета (ровный режим ≤ 4 ч/нед сессиями ≤ 2 ч; всплеск ≤ 25 ч не чаще раза в 6 недель), однопоточную очередь с формой задачи S/B и исполняемым столбцом «DoD-команда», который маркер запускает сам, а не доверяет галочке. Арифметика: спринт из 75–100 ч при 4 ч/нед — это 18–25 недель, при 8 ч/нед — 9–12; без этой записи маркер напечатает B при любом управлении.
3. *Политика ИИ-ассистированной разработки.* `CLAUDE.md` из трёх правил не закрывает корневой риск: ассистент, который пишет тест, чтобы он прошёл, и ставит галочку в STATE.md, воспроизведёт A7-01 в новой форме. Дополнение: политика живёт не прозой, а исполняемым suite `semantic-repo-policy-regression.cjs` с самопроверкой на заведомо плохих фикстурах: ратчет A7-01 (замороженный список suites, читающих исходники как текст, может только уменьшаться); «красный до» как реестр мутантов — новый suite принимается только с ≥ 1 мутантом в `prototype/lib`, который он убивает; seal-only коммиты для запечатанных фикстур, gold, baseline-хешей и чекбоксов (их меняет только автор).
4. *Механизм XFAIL/XPASS в run-all и политика классов хешей.* Сегодня `run-all.cjs` знает только статус процесса, литеральных SHA-256-пинов в тестах всего около десяти, и ставить политику надо до того, как программа добавит десятки. Критик не заметил реальную ловушку: печать v1 привязана к живому встроенному корпусу (`DEVELOPMENT_CORPUS_STALE` в evaluator), поэтому любое расширение вселенной доказательств (лечение A5-01) красит holdout-suite, и «естественный» ремонт — перепин `developmentCorpusHash` — тихо переподписывает seal. Дополнение: общий `check-harness.cjs` с `xfail: {id, issue}` (ожидаемый провал не красит suite, неожиданный проход — ошибка «снимите маркер»); ADR о классах хешей `SEALED / PINNED / DERIVED` с машинной проверкой перепина.

**Пробелы (внесены как поправки в §7–8):** реестр корпусов и предварительное разделение семейств источников (`benchmark/CORPORA.md`, `FAMILIES.json` до сбора D1 и корпуса шкал); единый словарь записи (controlled-lexicon + morph-table становятся словарём `ABSTAIN`, 28-леммный LEX semantic-core — `DIAGNOSTIC`); датированное решение по терминологии 1D/2D/3D и нумерации оболочек, вынесенное из-под запрета №6; статус самого docs/53 (снимок аудита, не источник полномочий).

**Противоречия (исправлены):** харнесс (нед. 3–10) должен был показать A3-01/A3-03 «красными сегодня», но те же дефекты закрыты в неделю 1 — поправка: в неделю 1 они закрываются юнит-тестами, харнесс кодирует как XFAIL оставшиеся A2-01/A2-04; «лимит прогонов v1 проверяется тестом» — поправка: норма с журналом; расписание экспериментов с людьми нарушало собственный запрет «один в квартал» — поправка в §8.3; четыре несогласованных числа для глоссария (≤ 4 / ≤ 9 / 25 / ≤ 40) — поправка: число величин определяется результатом «Четырёх шкал», не назначается; acceptance A2-02 «вставка „Связка“ не повышает guard» на неделе 1 недостижим без структурного фикса — поправка: на неделе 1 только измерение, фикс — месяц 2–3; «лемма-покрытие D1-b ≥ 85 %» на таблице из лексикона + D1-a количественно неправдоподобно — поправка в §8.4; STATE.md ≤ 3 КБ не вместит восемь видов записей — поправка: STATE.md держит только чекбоксы и журнал маркера, остальное — карточки и `experiments/`.

**Overclaim (сняты):** «теорема недостижимости CONTINUE» (показана grep-ом, это измеренный факт, а не теорема); «первый бенчмарк для русского» без сравнения с существующими наборами; «линтер смысла» для шести поверхностных правил; «0 литералов-порогов вне реестра к месяцу 3» (в `semantic-core.js` десятки inline-констант и 447 числовых литералов); «Два полюса подтверждают концепцию» — корреляция 0.3 с оценками 20 человек на 70 стимулах, построенных автором, не подтверждает форму `4λ(1−λ)`, а лишь даёт первую внешнюю опору для `u`.

Этот документ намеренно не принимает за автора трёх решений, без которых программа не начнётся: идентичность (ADR-000), критический путь и ёмкость (ADR-001), и готовность считать отрицательный результат результатом. ### 9.3. Приложение C — как воспроизвести ключевые измерения

Все команды выполняются из корня репозитория на Linux/macOS с Node ≥ 22 и Python 3; ничего устанавливать не нужно, кроме Playwright для браузерных проверок.

```bash
# 1. Полный детерминированный прогон (≈45 с): ожидается ALL PASS | suites 61/61 | checks 775/775
node prototype/tests/run-all.cjs

# 2. Статический сервер для P78 (file:// блокирует fetch data/*.json и, через A3-01, вставку хода)
python3 -m http.server 8787 --directory prototype
#    затем открыть http://127.0.0.1:8787/p78-living-ring-interface.html

# 3. Браузерные тесты под Chromium (в оригинале требуют Edge: channel 'msedge' в строках 198 и 85)
sed "s/channel: 'msedge', //" prototype/tests/browser-p78-neighbor-worlds.cjs > /tmp/nw.cjs
P78_BROWSER_BASE=http://127.0.0.1:8787/ TEMP=/tmp node /tmp/nw.cjs          # 24/24
sed "s/channel: 'msedge', //" prototype/tests/browser-p78-evidence-backed-link.cjs > /tmp/ebl.cjs
P78_BROWSER_URL=http://127.0.0.1:8787/p78-living-ring-interface.html TEMP=/tmp node /tmp/ebl.cjs   # 14/14

# 4. Зонд ядра (A2-01, A2-02, A3-03) — см. §5.3; загрузка модулей как в
#    prototype/tests/semantic-p78-action-controller-regression.cjs (global.window = global; require по списку)

# 5. Мутационный эксперимент (в отдельном worktree!): изменить порог и прогнать run-all
git worktree add /tmp/mut main && cd /tmp/mut
sed -i 's/else if(u<\.18)/else if(u<.40)/' prototype/lib/semantic-core.js && node prototype/tests/run-all.cjs | tail -1   # ALL PASS — мутация выжила
git checkout -- . && cd - && git worktree remove /tmp/mut

# 6. Инвентарные числа
git ls-files | wc -l                                   # 309
ls prototype/p*.html | wc -l                           # 80
wc -l prototype/lib/*.js | tail -1                     # 24869
grep -c '<script' prototype/p78-living-ring-interface.html   # 67
grep -ohE 'window\.MRD\w+' prototype/lib/*.js | sort -u | wc -l   # 39

# 7. Воспроизводимость инструментов данных
python3 -I tools/calibrate_phi.py     # OK, совпадает побитово кроме generated
```
